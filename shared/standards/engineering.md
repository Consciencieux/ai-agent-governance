# 工程判断

<a id="eng-01"></a>
## ENG-01 目标与结构

先明确目标行为、使用者、质量要求及当前约束，再决定实现位置和边界。对已授权能力完整实现；设计从目标系统出发，不能将“最小 diff”“先做简版”作为默认答案。

按语义所有权组织模块，集中同一事实和决策。拆分应减少职责混杂、重复推理或变化耦合；长度仅作为检查线索。需要整体重组时直接重组，清楚且符合目标的代码保持稳定。

禁止在错误归属处不断叠加补丁，或以降低文件数为由压平必要边界。方案已经确定时，实施按该方案推进。

<a id="eng-02"></a>
## ENG-02 复用与依赖

先查项目已有实现、配置和工具，再查标准库、运行时及成熟库。使用原有包管理器与锁文件；选择新依赖时核对实际 API、维护状态、许可、运行环境和必要的安全信息。

项目已有的适用技术栈继续使用。新选型优先稳定受支持的版本；存在 LTS 时优先考察 LTS。版本依据本次查到的官方资料确定。

禁止为减少依赖而重写解析器、加密、协议、数据库迁移器等通用基础设施，也禁止给成熟库再套一层无独立语义的包装。引入依赖带来的运行时、许可或部署变化按[授权标准](permissions.md#perm-01)处理。

<a id="eng-03"></a>
## ENG-03 机制与防御代码

新增抽象、状态、配置、重试、兼容分支或流程时，指出它解决的当前需求或可说明的失败风险。优先在已有负责人和边界内处理。

禁止以下无实际用途的结构：单一实现外的插件框架、只有常量的配置系统、重复多层的空值防御、恢复失败后的层层恢复、用 catch-all 返回成功掩盖错误，以及为方便测试而新增生产开关或钩子。

输入在信任边界验证，内部使用已建立的不变量。文件、网络和外部服务的真实失败保留恰当处理；重试只用于可恢复且具备重复执行条件的操作，明确停止条件。完整授权需求需要扩展点、并发控制或状态机时，设计并实现这些能力。

<a id="eng-04"></a>
## ENG-04 代码表达

采用项目的格式化、命名、类型和模块约定。用清楚的函数与数据关系表达行为；注释说明非显然的意图、约束和选择理由。

禁止逐行翻译代码的注释、空泛“增强健壮性”说明和无用途的防御性尾注。错误消息交代实际失败与可采取的动作。性能修改针对真实瓶颈，以测量或复杂度分析支持选择。

<a id="eng-05"></a>
## ENG-05 决策收敛

调查能够实质改变设计的未知；使用最有区分力的源码、官方文档、测量或小实验。选定方案后保留决定及关键依据，交给实施。

禁止用可选项、注册表和可配置策略藏起尚未作出的决定。无关优化留在任务之外；发现会使本次交付错误的依赖问题应一并解决，或明确所需的范围决定。
