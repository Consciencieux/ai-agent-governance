# 工程判断

<a id="eng-01"></a>
## ENG-01 目标与结构

从目标行为、使用者、质量要求和真实约束确定职责、接口与数据流。完整实现已批准的能力；禁止把最小 diff、文件最少或先做简版当默认设计目标。

结构应减少重复决策、职责混杂或变化耦合。需要整体重组时重组；符合目标的部分保持稳定。不要在错误位置不断加条件和适配层。文件明显难以理解时检查职责与依赖，按语义拆分、合并或删除，保持连贯的接口。

<a id="eng-02"></a>
## ENG-02 复用与依赖

先查项目原语、配置与工具，再选择标准库、运行时或成熟依赖。使用项目包管理器与适用的锁文件。新选型核对实际 API、维护状态、许可、运行环境及相关安全信息；已有合适依赖直接复用。

新选型优先稳定受支持版本，存在 LTS 时优先考察；既有项目按自身兼容范围工作。禁止仅为零依赖而重写通用解析、加密、协议或迁移基础设施，或添加没有独立职责的库包装。

接口适配、领域隔离和测试所需的真实边界按其用途设计。依赖变化造成原请求之外的许可、费用或部署影响时，按 [PERM-01](permissions.md#perm-01) 处理。

<a id="eng-03"></a>
## ENG-03 机制与防御代码

抽象、配置、状态、缓存、重试和流程应解决明确需求或合理的工程风险。判断其用途和成本后选择实现，正常设计无需逐项向用户自证必要性。

严格清理无用途的插件外壳、重复空值检查、层层恢复、测试专用生产开关，以及 catch-all 返回成功。配置文件、单实现接口和扩展点按实际用途判断，不能仅凭数量少就删除。

在信任边界验证输入，内部复用已建立的不变量。文件、网络、资源竞争和外部依赖的常见失败要有适当处理；重试考虑幂等性、失败类型、等待和停止条件。既有库已经负责的恢复由其负责。禁止为纯假设故障继续叠加恢复链或无消费者的兼容方案。

<a id="eng-04"></a>
## ENG-04 代码表达

采用项目的格式化、命名、类型和模块约定，用清楚的函数与数据关系表达行为。注释解释非显然的意图、约束和选择；删除逐行翻译、空泛“增强健壮性”及防御性尾注。

错误消息说明实际失败和有用的处理动作。性能设计依据复杂度、资源需求或测量；声称性能改善时使用可比较的观测。行尾和文本格式沿用仓库声明，避免无关的全文件格式改动。

<a id="eng-05"></a>
## ENG-05 判断与收敛

调查能够改变选择的未知，优先源码、官方文档、测量或有区分力的小实验。已有决定及其仍成立的前提可以复用；用户要求重评或出现相反证据时，重新检验前提、替代方案与当前结果，再作决定。

禁止用旧文档的 Accepted、Resolved 或“以前考虑过”代替本次重评，也禁止把未决选择藏进配置或注册表。任务规模和流程由风险、依赖与协调需要决定；文件数量和模糊的谨慎感不触发审批升级。

选择确定后实施。无关优化留在任务之外；影响本次正确性的关联问题及时处理，超出明确授权边界的部分说明影响并提出具体决定。
