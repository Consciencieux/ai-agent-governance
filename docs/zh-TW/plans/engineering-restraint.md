# 工程克制：反過度工程（對現有規則層的增補，TASK 計劃）

[English](../../en/plans/engineering-restraint.md) · [简体中文](../../zh-CN/plans/engineering-restraint.md) · [繁體中文](engineering-restraint.md)

> **狀態：已實作，待歸檔。** 本計劃把「Engineering Restraint — Anti-Overengineering」原則作為**對現有規則層的窄增補**落地：在 coding.policy.md 增加一個簡短小節（機制測試 + 兩條邊界），SKILL.md 加一行指標。不新建政策檔案、不新增門禁、不新增審查問題、不新增 TASK 欄位、不新增分發面。

**Target：both** —— 判據：既有語義所有者 coding.policy.md 已在 INIT 複製清單中（分發為 docs/rules/coding.md），增補它 = 複用既有分發通道、零新增複製面；不是「看似適合所有專案」就進 payload。

### 任務目的

把「Engineering Restraint」原則作為對現有編碼規範的窄增補落地，使 Agent 在實作已批准能力時直接、完整地交付，而不添加當前需求、風險或語義未獨立證明的機制。本計劃自身必須通過機制測試：只增補既有檔案一個小節加一行指標，不建新的治理子系統。

### 當前問題

- coding.policy.md 已有相近語義（不引入未被要求的抽象、不做無關重構、依賴與重型機制需說明、遵循架構與語義所有者），但缺少統一的決策檢查點，也缺少兩條防誤用邊界（已批准需求優先、語義接縫合法）。
- 本倉庫近期出現過多次「為修機制而繼續增加機制」的返工，說明這是需要提醒 Agent 的可泛化行為模式；這些案例僅作為動機，不自動轉化為永久門禁或事故專用流程。

### 提議方案

#### 1. 增補 coding.policy.md 一個小節（payload，零新增分發）

在 references/policies/coding.policy.md 增加簡短小節「工程克制與機制測試（Engineering Restraint / Machinery Test）」：

- 機制測試：新增任何非平凡之物前自問——「若它今天不存在，當前需求是否仍會獨立證明其必要？」 否 → 不加；是 → 用最窄的既有所有者或成熟機制解決；直接實作夠用就不插入框架或流程。流程也是機制：計劃、門禁、矩陣、審查步驟、檢查清單、證據工件與抽象、狀態、恢復系統同等舉證。
- 操作規則（壓縮）：直接完整實作已批准能力，不以「簡單」之名削減真實需求；優先既有語義所有者、既有原語、標準/Node/OS 能力、成熟函式庫；偏好有界真實失敗而非投機韌性；測試保護有意義契約，不因可測性製造生產 DI/工廠/鉤子；證據證明具體主張而非紀念單次事故；既有程式碼無自動保留特權，也不得無因翻動；未決重大判斷升級；授權行為與證明完成後停止。
- 邊界一（已批准需求優先）：本規則約束未經批准的新增機制，不否決用戶已批准的功能、架構決策、遷移要求、門禁要求或 TASK 計劃；若批准方案與工程克制衝突，必須升級決策，不得自行刪減需求。
- 邊界二（語義接縫合法）：允許為當前需求保留清晰的介面邊界、模組邊界、擴充點和穩定語義；禁止為尚不存在的消費者實作完整抽象層、設定系統、外掛機制、恢復鏈、通用框架或狀態機。

不新建 policy 檔案、不動 lifecycle.policy.md：coding 小節已可承載「流程也是機制」一句；若實作中發現無法承載再升級決策，不預設擴展第三個 policy。

#### 2. SKILL.md 指標一行

治理原則（policy 層）增加一行指標（檔案 + 章節），不複述內容。機制測試是 Agent 的決策檢查，不是文件交付物：不新增 TASK 欄位、不要求每個計劃寫機制證明、不要求額外記錄。

#### 3. 明確不做（機制測試的自用）

- 不新增機械門禁、評分、資格矩陣、審查階段、報告欄位、永久 checklist、machinery registry。
- review-manager 不新增問題：policy 已規定決策時自問；只有出現漏檢過度工程的具體證據時，才作為現有檢查項中的非獨立問題補上（不新增階段/欄位/證據/gate）。
- 不新增 init-spec 複製條目、layout 條目、principles index 行——全部經由現有所有者與現有分發。
- 不複製反補丁計劃領地：欠修（根因、失敗升級）歸反補丁計劃；過度建造歸本規則；刪除殘留歸變更歸位。

### 風險與決定

- 自諷風險：本計劃只增補一個既有檔案的小節加一行指標，不新增專門測試；治理價值來自規則文本在決策點的提示，而非新機器。
- 已批准需求邊界：Agent 不得藉「反過度工程」刪減已批准需求；衝突必須升級——防誤用的核心邊界。
- 語義接縫邊界：防止矯枉過正刪除合理的介面/模組邊界；未來機制需當前證據，未來結構不算缺陷。
- 與反補丁計劃邊界：反補丁治「修復不徹底」，本規則治「建造過度」。
- 無法機械化：判斷型原則由審查與批准執行，不由門禁執行。
- Target 判據：both 成立是因為既有所有者已是 payload 並隨 INIT 分發（複用既有通道），而非「看似適合所有專案」。

### 驗證方法

- coding.policy.md 的分發由現有 init-spec 複製不變量測試覆蓋（無新測試）。
- SKILL.md 指標人工核對可解析。
- npm run check / check:all 全綠（測試、parity、layout、--gate、交付對帳）。
- 人工檢查本次實作未新增 gate、狀態、欄位、審查階段、重複所有者。
