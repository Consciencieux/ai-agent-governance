# 變更歸位與殘留清理（TASK 計劃）

[English](../../en/plans/removal-hygiene.md) · [简体中文](../../zh-CN/plans/removal-hygiene.md) · [繁體中文](removal-hygiene.md)

> **狀態：已實作（2026-08-30，待 Release 歸檔）。** 本計劃已在目前工作樹交付；發佈時按倉庫規則歸檔。
>
> **Target: both** —— `payload` 交付給受治理專案（`SKILL.md`、`references/`）；`repo-infra` 維護本倉庫的 `AGENTS.md`、測試和開發者文件。兩類交付點分列在「受影響檔案」中。
>
> **目標版本：v0.11.0（暫定）**。這是面向 Agent 的行為規則；若最終只做文件整理，發佈時由 Release Proposal 按 SemVer 重新判定。實作階段不直接改版本或建立發佈。

### 任務目的

建立一條跨變更類型的**變更歸位與殘留清理規則**：修改完成後，當前規範層和當前實作層只表達現行事實；相容/遷移資訊進入明確的過渡層；變更原因和歷史事實進入歷史層。這樣刪除、重新命名、遷移、替換或拆分合併後，後續 Agent 不會被過時的詞、連結、設定、範例或互相矛盾的描述誤導。

「刪除即刪淨」只是其中一種情況，不是完整規則。規則必須同時保護程式碼、設定、測試、CI、範本、產生物和三語文件之間的語義一致性。

### 當前問題

- 原計劃只涵蓋刪除/替換後的否定式註腳，未涵蓋重新命名、移動、棄用、遷移、拆分、合併、關閉 feature flag 或修改 API/資料格式後的殘留。
- 「用舊名稱全倉搜尋，命中數必須為零」過於粗糙：CHANGELOG、ADR、歸檔計劃、遷移指南、相容別名和相容測試可能必須保留舊名稱；真正需要清零的是當前規範層中未獲批准的殘留。
- 只修改單一事實來源而不更新引用、錨點、動態載入名稱、環境變數、測試 fixture、產生物或翻譯，會產生「程式碼已變、治理仍舊」的漂移。
- 刪除公開介面、設定或資料格式時，如果沒有呼叫方盤點、遷移方案、相容窗口和回滾條件，容易把清理誤做成無意的破壞性變更。
- 本次會話的具體舊內容、影響面和可接受相容範圍必須以實際搜尋結果為準，不能由 Agent 憑印象判斷「已經刪乾淨」。

### 術語與分層

所有命中都先按所在表面分類，再判斷是否為殘留：

| 表面 | 內容 | 可以提及舊內容嗎？ |
| --- | --- | --- |
| **當前規範/實作層** | 當前 `AGENTS.md`、`docs/rules/**`、當前架構/功能/命令文件、程式碼、設定、schema、CI、測試和 Agent 實際讀取的產生物 | 預設不可以；只能保留仍然工作的相容行為或必要的遷移指標 |
| **相容/過渡層** | deprecation/migration 文件、相容別名、adapter、feature flag 過渡邏輯、相容測試和版本遷移說明 | 可以，但必須寫明用途、範圍、責任人和移除條件/版本；不得讓舊內容看起來仍是首選行為 |
| **歷史層** | `CHANGELOG.md`、ADR、`docs/archive/` 和已完成計劃的歷史記錄 | 可以；這裡記錄事實、原因和決策，不作為當前執行規則 |
| **計劃/審查層** | 未完成計劃、審查報告和任務報告 | 可以用於描述問題和驗收，但不得被誤當作執行期規則；完成後按歸檔規則保留歷史 |

因此，判斷標準不是「舊詞在倉庫中出現次數為零」，而是：**當前層沒有未解釋、未批准、會誤導執行的舊事實；相容層的每個例外都有明確退出條件；歷史層的記錄不被當前 Agent 當作指令。**

### 適用的變更類型

| 變更類型 | 必須檢查 | 舊內容的預設處理 |
| --- | --- | --- |
| 刪除/移除 | 引用、匯出、註冊表、路由、設定、環境變數、文件、範例、測試、CI、產生物、連結和遷移影響 | 從當前層清除；歷史層保留原因；公開契約必須給出遷移或不需要遷移的證據 |
| 重新命名/移動 | import、動態載入、外掛名稱、路徑、連結、錨點、命令觸發詞、設定鍵、環境變數、Feature/Architecture 登記和三語副本 | 當前層統一新名稱；舊名只在明確相容別名或遷移說明中保留，並標記期限 |
| 替換/改寫 | 新舊語義是否矛盾、單一事實來源、範例、預設值、schema、測試斷言和產生輸出 | 當前層只描述新行為；舊行為說明進入遷移/歷史層，不能用否定式註腳污染當前規則 |
| 棄用/軟刪除 | 首選新路徑、相容窗口、警告、責任人、移除版本、呼叫方通知和測試 | 舊內容可在相容層存在；必須可識別為非首選，並有可執行的收口條件 |
| 拆分/合併/重組 | 歸屬、所有者、來源檔案、交叉引用、目錄索引、重複正文和同步組 | 當前層只保留一個權威來源；遷移映射放在過渡層，避免兩份正文繼續分叉 |
| 關閉/移除設定或 feature flag | 預設值、schema、環境範例、CI、部署腳本、執行期分支、測試 fixture 和文件 | 明確是暫時關閉、棄用還是徹底移除；不能讓已關閉能力看起來仍可用 |
| API/CLI/協定/資料格式變更 | 外部呼叫方、版本相容、序列化、回滾、遷移腳本、release notes 和 SemVer | 沒有相容方案不得靜默移除；破壞性影響必須走高風險審查和發佈判定 |
| 範本/產生物/翻譯變更 | 源檔案、產生檔案、既有專案遷移、三語結構、連結和版本漂移 | 先確定源頭；透過明確流程更新投影；不得靜默覆蓋既有專案 |
| 權限/安全/校驗規則變更 | 保護範圍、權限邊界、失敗閉環、回滾和使用者確認 | 不能以「清理殘留」為由放寬限制或移除閘門 |

### 提議方案

#### 1. 建立變更清單（Change Hygiene Ledger）

中/大型變更在計劃的「受影響檔案」之外，增加一張變更清單；小型單檔文件改動可在最終報告中使用精簡版。每個被移除、改名、替換或遷移的概念/路徑/介面都要有一行：

| ID | 類型 | 舊項 → 新項 | 影響表面 | 處理決定 | 允許舊引用/退出條件 | 證據 |
| --- | --- | --- | --- | --- | --- | --- |
| CH-01 | rename | `old` → `new` | code/docs/config | 全量改名，保留相容別名至 vX | `docs/migration.md`；vX 移除 | `rg` + 測試 |

處理決定只能是 `remove`、`rename`、`replace`、`deprecate`、`retain` 或 `migrate`。沒有決定、所有者、退出條件或證據的條目視為 `unresolved`，不能宣稱完成。

#### 2. 變更前：發現影響面

在修改前，Agent 必須：

1. 記錄舊名、舊路徑、舊設定鍵、舊命令、舊 schema 欄位、舊 feature 名和可能的動態字串；不要只搜自然語言標題。
2. 使用 `rg` 搜尋程式碼、設定、文件、測試、CI、範本、產生物和三語樹；另外檢查外掛、反射、字串串接、manifest、環境變數和腳本參數。
3. 將每個命中放入當前層、相容層、歷史層或 `unresolved`；搜尋到的檔案進入 Affected Files。
4. 先確定是「徹底移除」還是「相容遷移」。如果存在公開呼叫方、動態引用或未知消費者，預設按高風險/阻塞處理，不能直接刪除。

#### 3. 變更中：先改權威源，再收斂投影

- 先更新單一事實來源，再同步 AGENTS 指標、規則檔案、架構/Feature 登記、程式碼引用、設定、測試、CI、範本、產生物和翻譯。
- 當前規範層只寫現行行為；不要用「已刪除」「不再支援」「這裡曾經……」等註腳代替清理。若使用者確實需要知道遷移方式，把說明放入相容/遷移層並給出退出條件。
- 重新命名或移動時，相容別名、重新導向、shim、adapter 必須是有意保留的條目，並在變更清單中聲明，不得因為「全倉零命中」而誤刪。
- 刪除程式碼前仍必須遵守刪除保護：說明原因、確認歸屬、搜尋引用、檢查 Feature Registry 影響、提供遷移/回滾方案；動態呼叫和設定驅動路徑必須人工核驗。
- 不把 CHANGELOG、ADR、歸檔計劃中的歷史描述複製回當前規則或正文；當前文件只引用規則源，不重複規則正文。

#### 4. 變更後：按表面做定向清理

驗證分為四類，不再使用單一的「全倉命中數」：

- **當前層檢查**：舊識別符、舊連結、舊錨點、舊設定鍵、舊命令和舊語義的未解釋命中必須為零。
- **相容層檢查**：每個保留命中都在變更清單中有理由、範圍、責任人、移除版本/日期和對應測試或遷移文件。
- **歷史層檢查**：CHANGELOG、ADR、歸檔和計劃可以保留舊內容，但當前 Agent 的執行路徑不得把它們當作現行規則。
- **投影一致性檢查**：程式碼/設定/測試/CI/範本/產生物/三語文件之間沒有斷鏈、重複權威源或互相矛盾的說法。

任一命中無法分類、公開消費者無法確認、相容邊界未決定、產生物未更新或遷移/回滾未驗證，任務標為 `⚠️ Blocked` 或 `❌ Failed`，不得用否定式註腳掩蓋。

#### 5. 接入生命週期

- **Phase 1 Understand**：讀取架構、Feature、規則和最近 CHANGELOG，識別變更類型與舊/新項。
- **Phase 2 Plan**：中/大型計劃必須包含 Change Hygiene Ledger、相容性決定、遷移/回滾方案、Affected Files 和 Target。
- **Phase 3 Implement**：按「權威源 → 引用 → 投影」順序修改，逐項更新清單。
- **Phase 4 Validate**：執行當前層/相容層/歷史層/投影檢查及標準測試、靜態檢查、建置和文件閘門。
- **Phase 5 Synchronize**：同步 CHANGELOG、ADR、Feature、Architecture、三語文件和計劃狀態；歷史原因只寫歷史層。
- **Phase 6 Report**：報告已移除/改名/替換/棄用項、保留的相容項及退出條件、未解決命中、遷移/回滾結果和真實驗證證據。

這條規則適用於小型改動，但小型改動可以使用精簡清單；涉及公開介面、權限安全、資料格式、跨模組重組或未知動態引用時，按大型改動執行並進行深度審查。

#### 6. 規則落點與遷移

實際規範正文放在 `references/policies/lifecycle.policy.md`（必要時由 `coding.policy.md` 添加指標），生成專案的 `docs/rules/` 由源檔案複製；`SKILL.md` 和本倉庫 `AGENTS.md` 只保留指標或摘要，不複製完整規則。

既有治理專案不會因源範本變化自動更新。明確升級時按 MIGRATE 流程合併生命週期/編碼規則、Agent 摘要和相關產生物，保留既有相容安排，並執行目標專案 validator；不得把一次清理任務偷偷變成全專案重構。

### 受影響檔案

#### Payload（交付給受治理專案）

- `references/policies/lifecycle.policy.md` —— 作為變更歸位與殘留清理的權威規則，加入四層表面、Change Hygiene Ledger、變更矩陣、生命週期接入和驗證標準
- `references/policies/coding.policy.md` —— 將 Code Modification / Deletion Protection 指向通用變更清單，並補充重新命名、遷移、棄用和公開契約檢查
- `references/templates/agents-md.template.md` —— 增加精簡摘要/指標：變更前搜尋影響面、區分當前/相容/歷史表面、沒有未解釋殘留；不在範本複製完整矩陣
- `SKILL.md` —— 只增加指向權威 lifecycle/coding policy 的入口說明（不複製正文；若現有入口已足夠則不改）

#### Repo-infra（本倉庫維護）

- `AGENTS.md` —— 增加本倉庫貢獻者可執行的變更歸位指標；遵守本倉庫的 payload/repo-infra 分層，不重複規則正文
- `tests/run-tests.js` —— 增加當前層零殘留、相容層元資料、動態引用/連結、產生物/三語同步和遷移相容的契約測試
- `docs/en/anti-regression.md`、`docs/zh-CN/anti-regression.md`、`docs/zh-TW/anti-regression.md` —— 更新開發者機制地圖，說明該規則覆蓋的變更類型
- `docs/en/lifecycle.md`、`docs/zh-CN/lifecycle.md`、`docs/zh-TW/lifecycle.md` —— 更新生命週期摘要，指向完整變更清單規則
- `docs/glossary.md` —— 如新增 Change Hygiene、compatibility surface、historical surface 等術語，先補三語詞條
- `CHANGELOG.md` —— 在 `[Unreleased]` 記錄行為變化（`Changed`）；不為每次業務清理單獨建立版本條目

本計劃的三語副本也必須同步。只有在新增/修改觸發詞或子技能時，才將 `docs/en/commands.md`、`docs/zh-CN/commands.md` 和 `docs/zh-TW/commands.md` 加入；本計劃本身不新增提示詞。發佈時按 Release 流程同步版本、歸檔計劃和 roadmap，實作階段不自動執行。

### 風險與緩解

- **規則過寬導致 Agent 不敢改動**：按變更類型分級；只阻斷未分類、影響公開契約或涉及安全/權限的高風險項，小型明確改動使用精簡清單。
- **全倉零命中誤傷相容/歷史記錄**：搜尋仍覆蓋全倉，但驗收按四層表面分類；相容例外必須有退出條件。
- **動態引用漏檢**：把字串、外掛註冊、manifest、環境變數、腳本參數和產生物列為強制搜尋面；無法確認時阻塞，不假設沒有消費者。
- **刪除被錯誤變成破壞性變更**：公開 API/CLI/協定/資料格式變更必須有呼叫方盤點、遷移、回滾和 SemVer 判定。
- **多處權威源分叉**：先改源檔案，再更新投影；AGENTS/SKILL/docs 只做摘要或指標，不能複製正文。
- **相容層無限期殘留**：每個別名、shim、舊設定或 deprecation 條目必須有責任人、移除版本/日期和測試；到期由後續清理任務處理。
- **安全閘門被「清理」掉**：權限、安全、刪除保護和校驗步驟的修改繼續走治理檔案保護及高風險審查，不能用本規則降低門檻。
- **三語/產生專案漂移**：源文件、三語文件和既有專案遷移分別驗證；產生器不覆蓋既有檔案。

### 驗收與驗證方法

#### 自動/契約測試

- 變更清單能表達 `remove`、`rename`、`replace`、`deprecate`、`retain`、`migrate`；缺少決定或證據的條目不能標記為完成。
- 當前層的舊符號、舊路徑、舊連結、舊錨點、舊設定和舊語義命中會被報告；CHANGELOG/ADR/歸檔中的合法歷史命中不會被誤報為殘留。
- 相容層命中缺少責任人、退出版本/日期、遷移說明或測試時會失敗；有完整元資料時通過。
- 模擬刪除、重新命名、替換、棄用、feature flag 關閉、拆分合併、API/資料格式變更，分別驗證引用、設定、測試、CI、產生物和文件同步。
- 動態字串/外掛註冊/manifest/環境變數 fixture 能被發現；未知公開消費者或未分類命中進入 `Blocked`。
- 舊範本/舊 `state`/舊活動記錄和既有治理專案通過 MIGRATE fixture 後仍可讀取；既有檔案不被自動覆蓋。

#### Agent 行為驗收（狗糧場景）

構造一個同時包含：刪除內部文件段落、重新命名設定鍵、保留帶截止版本的相容別名、棄用公開命令和移動產生範本的任務，檢查：

1. Agent 在修改前輸出舊/新項、影響表面、處理決定和 Affected Files。
2. 當前層只保留現行名稱和行為；相容層明確用途、責任人和退出條件；歷史層保留原因；不在當前規則加入「已刪除/不再……」式註腳。
3. 未分類命中、動態引用不明或遷移未完成時不能宣稱完成；狀態和報告寫明阻塞原因。
4. 重複執行不產生重複權威源；產生物和三語文件保持一致。
5. 若變更涉及公開契約或安全規則，出現單獨的審查/確認記錄、遷移或回滾證據和正確的版本分類。

#### 本倉庫閘門

- 本倉庫執行 `npm test`、`npm run check`；不執行或偽造預設 `scripts/verify_governance.js` 的通過結果。
- 修改 `references/`、腳本或三語文件後執行 `docs:parity`、`docs:layout`、`check-doc-consistency.js`，並記錄真實輸出。
- 執行一次 `rg` 影響面複核，解釋每個未分類命中，並用 `git diff --name-only` 對照計劃的 Affected Files 和 Target。
