# 交付錨點（TASK 計劃）

[English](../../en/plans/plan-delivery-anchors.md) · [简体中文](../../zh-CN/plans/plan-delivery-anchors.md) · [繁體中文](plan-delivery-anchors.md)

> **Status: implemented.**（已實現。）於 v0.13.2+（2026-09-06）交付：交付閘門新增錨點語法（`— anchor: `snippet``）；帶錨點的已存在路徑按**內容**驗證，而非僅存在性。與計劃的偏差（刻意）：未實施凍結基線清單——嚴格從當日起的錨點要求取代它，因計劃自身 Risks 節警告「大凍結清單會從發佈日起弱化規則」。兩個迴歸測試 + 變異驗證。見 CHANGELOG（邊界拆分批次）。

**Target：repo-infra** —— 交付門禁與其測試屬倉庫基礎設施，宣告規範落在 `AGENTS.md`。本計劃不產出任何進入被治理專案的內容。

### 任務目的

讓交付門禁驗證宣告的內容真的落進了宣告的檔案。計劃指名一個落地點，就要指明落地的是什麼，門禁要能找到它。

### 當前問題

- 門禁驗證宣告路徑的方式是查檔案是否存在。對樹中本就存在的檔案，存在性在計劃寫下之前就已滿足，於是無論計劃承諾了什麼，檢查都報成功。
- 本次會話實例：`removal-hygiene` 宣告了 `AGENTS.md` 與 `SKILL.md` 兩個落地點，兩個檔案都沒拿到那條規範。門禁報 28 plans verified，exit 0。缺口是人工通讀發現的——而這正是門禁本該替代的那道保障。
- 行為宣告（`writes:` / `wires:`）確實驗證內容，但計劃要主動採用該語法才享有驗證。最可能不採用的，恰恰是用散文宣告普通檔案的普通計劃。
- 覆蓋面因此是反的：新建檔案的計劃被嚴格檢查，改動既有治理檔案的計劃被空洞檢查——而本倉庫多數計劃做的就是改動既有治理檔案。

### 提議方案

- **錨點要求**：Affected Files 中若宣告的路徑早於本計劃存在，則該條附帶錨點——本次改動寫入該檔案的一小段引用文字。`AGENTS.md` —— 錨點：`刪除即刪淨`。門禁在目標檔案中搜錨點，找不到即失敗。
- **先後判定**：比較宣告路徑的新增提交與計劃文件的新增提交（`git log --diff-filter=A -1`）。路徑新增更早，或計劃尚未提交，則判定路徑早於計劃，需要錨點；路徑由本計劃引入，則存在性仍是有效證據。
- **基線豁免**：本規範之前寫就的計劃記入門禁腳本內的凍結清單，要求只對清單之外的計劃生效。測試斷言該清單不被追加，新計劃無法混入。
- **無 git 兜底**：拿不到 git 中繼資料時，門禁把既有路徑判為早於計劃，並以諮詢方式報告錨點要求而非直接失敗，使檢查在倉庫匯出副本中仍可執行。
- **規範落地**：AGENTS.md 中關於計劃宣告的規則，在既有 Target 欄位規則旁增加錨點要求。

### 受影響檔案

- repo-tools/check-plan-delivery.js —— 錨點解析、先後判定、凍結基線
- tests/suites/*.test.js —— 覆蓋下列驗證場景的迴歸(run-tests.js 只是發現入口;在其中註冊測試會使衛生閘門失敗)
- AGENTS.md —— 計劃宣告規範中的錨點要求
- CHANGELOG.md —— 門禁行為變更

### 風險

- **遷移量**：歸檔計劃普遍宣告既有檔案，基線正是用來吸收它們的。選定切分點前先量出數量——凍結清單一旦很大，規則從上線當天就是弱的。
- **錨點漂移**：措辭日後被改寫，錨點即失效，健康的樹上門禁也會變紅。錨點優先取穩定術語；錨點失效按修正計劃處理，而非給門禁開豁免。
- **git 依賴**：先後判定讀取倉庫歷史；兜底讓門禁在歷史不可得處降為諮詢，而那恰恰是計劃被四處複製的環境，驗證強度在那裡最弱。

### 驗證方法

- 重現 `removal-hygiene` 場景：計劃宣告既有檔案且無錨點，門禁轉紅並指名該計劃。
- 錨點存在於目標檔案則通過；錨點缺失則失敗並指名該錨點。
- 由計劃自身新建的路徑仍靠存在性通過，確認對 `references/templates/githooks-template.md` 不產生誤報。
- 凍結基線測試在清單被追加時失敗。
- `npm run check` 與 `npm run check:all` exit 0，測試數上調。
