# 治理缺陷閉環——同類實例與控制面追查（TASK 計畫）

[English](../../en/plans/governance-defect-closure.md) · [简体中文](../../zh-CN/plans/governance-defect-closure.md) · [繁體中文](governance-defect-closure.md)

> **Status: design plan, not implemented.** 窄版雙域條款已作為基礎落地，但本計畫只有在同時防止局部修復和只修輸出後才算完成。

**Target: both** —— `payload` 修改被治理專案收到的修復協定；`repo-infra` 更新 skill 執行指標、生成指引、目標鏈路測試、CHANGELOG，以及本計畫/路線圖索引。

## 本計畫必須解決的兩個原始問題

### 問題一——修復一個實例，卻不排查同類實例

發現有缺陷的規則、範本、腳本、閘門、測試、發佈條目、生成產物或同步文件後，Agent 往往只修復當前行，不搜尋共用同一契約的其他實例。

計畫必須要求在相關同類表面進行有界搜尋，並寫明搜尋範圍和命令或枚舉方式；「沒有發現其他問題」本身不算證據。

### 問題二——修復輸出，卻不追查控制面

Agent 可能只修復缺陷的可見輸出或投影，卻不檢查產生或漏檢它的規則、範本、產生器、閘門、測試預言機、發佈流程或目標投影。因此問題可能再次出現，或在下一次生成時被覆蓋。

計畫必須要求檢查相關控制面鏈路，同時覆蓋來源到輸出和輸出到消費者兩條路徑。

這兩個問題屬於同一類失敗：局部修復在影響面和生產鏈檢查完成前就停止。

## 工程克制邊界

計畫不新增通用相似度引擎、萬能審計註冊表、強制五層表格、新閘門或新狀態體系。繼續使用現有的 `repairSessionId`、影響面搜尋、變更衛生對帳和 `mutation-probe.js`。

## 提議方案

### 1. 雙域對稱（寫入 `lifecycle.policy.md` 根因修復協定）

治理缺陷往往同時活在兩個域——編寫規則的一側和執行規則的一側。只修復被報告的那一側、預設另一側正確，是已被多次證實的漏修模式。

- 缺陷出現在專案自身的規則/指令碼/閘門 → 必須檢查它的來源與投影：生成該檔案的範本或生成器、對應的檢查器、以及規則文字本身是否也帶同一錯誤。
- 缺陷出現在生成產物或分發產物 → 必須檢查產生它的原始檔與分發鏈路，不能只改產物（下次生成會覆蓋）。
- 對應域不存在或不適用時必須寫明具體原因，不得預設正確、不得靜默略過。

### 2. 同類實例閉環

當缺陷屬於治理契約而不是孤立措辭錯誤時，Agent 必須在聲明的相關表面枚舉同類實例後再完成。搜尋範圍可包括：

- 同一目錄、腳本族、硬編碼枚舉或同步文件集合；
- 源規則、範本、產生器、生成投影和相容層；
- repo-infra 與被治理專案的對應實作；
- 同一批次修改的相關檔案。

每個表面必須給出簡短結果：已修復、有證據證明正確、不適用並說明原因，或因前置條件缺失而阻塞。結果記錄在現有 `repairSessionId` 中，不新增註冊表。

### 3. 控制面追查

Agent 必須檢查與缺陷相關的生產鏈和執行鏈，不能盲目執行無關清單。對於格式或輸出缺陷，通常包括：

```text
權威規則 → 範本/產生器 → 輸出
→ 檢查器/閘門 → 測試預言機 → 發佈或目標消費者
```

對於 payload 缺陷，還必須檢查 tarball → INIT → 乾淨目標專案。對於 repo-only 缺陷，目標消費者可以是本倉庫的發佈或開發流程。每個相關層都必須修復、用證據證明正確，或明確標記為阻塞/不適用。

任何可見輸出缺陷都不能只編輯輸出檔案。必須識別並檢查適用的權威規則、產生路徑、執行路徑、證據路徑以及發佈或目標消費者邊界；不適用的層必須明確說明理由。

### 4. 有界負向驗證

當某個閘門/檢查器聲稱能攔截該缺陷時，用一次有界的負向驗證證明它不是空轉：在隔離夾具中重新注入缺陷 → 該檢查必須失敗；恢復正確形式 → 必須通過。只對可判定的閘門行為要求，不要求語意判斷做變異。

已有 `mutation-probe.js` 可承載此項，不新增機制。

### 5. 適用域與停止條件

本計畫只適用於治理規則、範本、生成器、閘門、測試、生成產物、同步治理文件與發佈流程；普通業務程式碼與孤立措辭錯誤不觸發。

相關同類表面都有證據結果、相關控制面已檢查、對應域已檢查，並記錄適用的回歸/閘門證據後即可停止。

### 6. 本次明確不新增

- 通用相似度引擎
- 萬能審計註冊表
- 強制五層審查表
- 僅為本協定新增的閘門或審計指令碼

## 與現有協定的關係

- 現有 `repairSessionId`、先復現欄位和失敗預算仍是會話與升級機制。
- 本要求補充而不是取代影響面搜尋和變更衛生對帳。
- 同類實例與控制面結論記錄在現有修復會話中，不引入新的註冊表或升級步驟。
- `mutation-probe.js` 是現有工具，本條僅為使用它的場景增加一條觸發條件。

## 驗證方法

1. 三語 parity 和計畫狀態閘門通過。
2. 夾具證明發現一個同類實例後，相關同類搜尋能報告另一個實例；不新增相似度引擎。
3. 輸出或投影夾具證明報告會檢查適用的權威規則、產生路徑、執行路徑、證據路徑以及發佈/目標消費者邊界，而不只檢查輸出。
4. payload 修改通過 tarball → INIT → 乾淨目標專案驗證。
5. 閘門聲稱能捕獲該缺陷時，使用 `mutation-probe.js` 或其他已有的有界檢查，證明重新注入會失敗、恢復後會通過。
6. `npm run check` 全綠。

## 完成條件

- `lifecycle.policy.md` 根因修復協定要求同類實例和相關控制面閉環。
- repo-infra 與被治理專案的執行路徑都能讀到同一要求。
- 觸發缺陷不能只修復可見輸出或單一域後就宣告完成。
- AGENTS.md 原則指標指向該檔案。
- `npm run check` exit 0。
