# 治理缺陷閉環——同類實例與控制面稽核（TASK 計畫）

[English](../../en/plans/governance-defect-closure.md) · [简体中文](../../zh-CN/plans/governance-defect-closure.md) · [繁體中文](governance-defect-closure.md)

> **Status: design plan, not implemented.** 本計畫補充現有根因修復協定的缺口：修復被報告的實例，並不等於已經閉合同一缺陷類別，也不等於審查了允許該缺陷產生、傳播或漏檢的規則、範本、產生器、閘門、測試和發佈鏈路。

**Target: both** —— `payload` 修改被治理專案 Agent 獲得的修復協定；`repo-infra` 更新 skill 執行指標、生成的 Agent 摘要、目標鏈路測試、CHANGELOG，以及本三語計畫/路線圖索引。兩類檔案分別列在 Affected Files 中。

## 任務目的

讓已確認的治理缺陷在缺陷族層面閉合，而不是只修復被報告的檔案或行。修復必須同時覆蓋兩個維度：

1. **橫向閉環** —— 枚舉並處理同一缺陷簽名的同類實例。
2. **縱向閉環** —— 檢查產生、傳播或未能發現該缺陷的控制面鏈路。

本計畫只適用於治理行為、規則、範本、產生器、閘門、測試、發佈記錄和生成產物。不把普通拼寫錯誤自動升級為全倉庫審查。

## 適用域與雙域對稱

這是一個雙域協定，同時適用於本 skill 倉庫（`repo-infra`）和接收 payload 的被治理專案；只在其中一個域實作並不算完成。

- 首先在 `repo-infra` 發現的缺陷，必須檢查對應的 payload 規則、範本、產生器、閘門、測試和目標專案投影。
- 首先在被治理專案發現的缺陷，必須檢查本倉庫中對應的來源檔案和分發鏈路。
- 對本倉庫，`AGENTS.md` 和 skill 執行指引必須要求 Agent 執行閉環；對被治理專案，分發的生命週期規則、`SKILL.md` 和生成的 `AGENTS.md` 必須提出同樣要求。
- 必須做反向檢查：同時檢查來源到產物、產物到消費者的路徑，包括生成產物和發佈打包。

如果只修復一個域中的報告實例，卻預設另一個對應域正確，則不得聲稱完成。

## 當前問題

現有根因修復協定已經要求重現、修復會話、失敗預算和回歸驗證，但沒有明確要求 Agent：

- 發現一個實例後搜尋同一缺陷模式的全部實例；
- 同時檢查權威規則、範本、產生器、閘門、測試和目標專案投影；
- 區分產物錯誤、規則錯誤、傳播錯誤、執行錯誤和證據錯誤；
- 對本應捕獲該缺陷的閘門重新注入缺陷，證明它確實會變紅。

這會形成局部修復模式：

```text
報告實例 → 修復實例 → 命令變綠 → 宣布完成
```

要求的模式是：

```text
報告實例 → 缺陷簽名 → 同類實例枚舉
→ 控制面審查 → 修復全部適用表面
→ 負向/變異證據 → 目標環境驗證
```

## 提議方案

### 1. 修復觸發與缺陷簽名

在根因修復協定中增加**閉環觸發條件**。當已確認缺陷涉及規則、範本、產生器、閘門、測試、發佈格式、生成產物、共享枚舉或同一變更批次時觸發。普通孤立措辭錯誤如果沒有暴露更廣泛的規則或投影問題，仍不在範圍內。

閉環開始時記錄簡短的 `defect signature`，包括：

- 可觀察到的失敗；
- 被違反的不變式或契約；
- 可能產生其他實例的模式；
- 受影響的受眾和執行環境；
- 必須枚舉的搜尋表面。

簽名綁定現有的 `repairSessionId`，不新增第二個會話或註冊表。

### 2. 橫向閉環：同類實例

Agent 必須在所有可能承載該契約的表面上枚舉同一簽名：

- 同一目錄、腳本、分支和硬編碼枚舉；
- 源規則、範本、產生器、生成投影和相容層；
- payload 與 repo-infra 對應實作；
- 多語言投影和同步文件；
- 生命週期階段和執行環境；
- 同一批次中修改的相關檔案。

每個枚舉到的實例必須明確給出一種結果：

```text
fixed
already correct（附證據）
not applicable（附原因）
blocked（附缺少的前置條件）
```

「沒有找到其他匹配項」本身不算證據；報告必須寫明搜尋表面以及使用的命令或枚舉方式。

### 3. 縱向閉環：控制面審查

治理缺陷必須檢查完整控制面鏈路：

```text
權威規則
→ 範本/產生器
→ 實作或生成產物
→ 閘門/檢查器
→ 測試預言機
→ 發佈/歸檔流程
→ 目標執行環境
```

每一層都必須判斷它屬於：

- 缺陷來源；
- 傳播該缺陷的路徑；
- 本應捕獲但沒有捕獲的執行缺口；
- 允許空洞綠燈的證據缺口；
- 已正確、無需修改的層。

例如 CHANGELOG 格式錯誤，不能只改 CHANGELOG。必須檢查格式規則、生成的 AGENTS 指引、結構檢查器、相關測試預言機、發佈流程和生成後的被治理專案形態。

### 4. 證據與變異要求

現有證據等級繼續作為權威：每個結論必須標註機械、人工背書或未驗證。

當某個閘門、測試或檢查器按設計應該發現該缺陷時，修復必須包含一個有界的負向檢查：

```text
在隔離夾具中重新引入缺陷 → 檢查應失敗
恢復正確形式 → 檢查應通過
```

這只適用於可判定的閘門行為，不要求每個語義判斷都做變異，也不引入通用 mutation testing 框架。

### 5. 範圍與停止條件

只有滿足上述觸發條件時才要求閉環掃描。滿足以下條件即可停止：

- 缺陷簽名已在聲明的搜尋表面上完成枚舉；
- 每個適用實例都有結果；
- 每個失敗的執行層都已修復，或明確標記為 blocked；
- payload 變更已在目標環境檢查；
- 原始回歸和相關閘門在負向檢查後通過。

不得添加通用相似度引擎、萬能稽核註冊表，或僅為記錄清單而新增通用閘門。將來某類缺陷反覆出現且可機械判定時，再通過獨立計畫增加窄範圍閘門。

## 與現有協定的關係

- 現有 `repairSessionId`、先重現欄位和失敗預算仍是會話與升級機制。
- 閉環要求補充 impact-face 搜尋和變更衛生對帳，不替代它們。
- 現有失敗預算後的 review-manager 升級仍然有效；閉環不能繞過開發者裁定或確認邊界。
- 綠色閘門仍只有其聲明的證據等級；閉環不能把機械證據升級為語義正確性聲明。

## Affected Files

**payload：**

- `references/policies/lifecycle.policy.md` —— 在根因修復協定中增加閉環觸發、缺陷簽名、橫向同類閉環、縱向控制面審查和有界負向檢查要求
- `SKILL.md` —— 將 AUDIT 和修復編排指向閉環修復協定，防止 skill 執行器停在報告實例
- `references/templates/agents-md.template.md` —— 如果生成的 AGENTS 契約需要操作性指標，則攜帶面向被治理專案的修復摘要

**repo-infra：**

- `tests/suites/payload.test.js` —— payload 契約修改後，驗證閉環條款進入乾淨的 Phase C 目標專案
- `AGENTS.md` —— 如果實作後的規則成為本倉庫的持久治理原則，增加純指標原則索引條目
- `CHANGELOG.md` —— 在發佈邊界記錄 payload 行為變更
- `docs/{en,zh-CN,zh-TW}/plans/governance-defect-closure.md` —— 本計畫
- `docs/{en,zh-CN,zh-TW}/roadmap.md` —— 在適當路線圖階段連結活躍計畫

本計畫不包含通用缺陷註冊表、相似度引擎或萬能閘門。

## 風險與裁定

- **範圍膨脹：** 缺陷簽名可能寫得過寬。緩解：要求命名搜尋表面和觸發條件；普通文件改動仍不觸發。
- **儀式化閉環報告：** Agent 可能列出表面卻沒有檢查。緩解：要求真實命令輸出或明確人工背書/未驗證標記，並要求閘門類缺陷提供負向檢查。
- **過度測試：** 每個可能變異都執行會重新製造過重機制。緩解：每個受影響執行契約只做一個有界負向夾具。
- **載荷漂移：** 只改規則、不檢查生成專案會重演「編寫環境正確、執行環境錯誤」。緩解：payload 變更執行 tarball → INIT → 目標閉包鏈路。
- **責任未決：** 控制面層屬於其他計畫或責任人時，標記為 blocked 並寫明前置條件，不得靜默省略。

## 驗證方法

1. 執行三語 parity 和計畫狀態閘門。
2. 實作時證明閉環觸發存在於 skill 執行器和生成的被治理專案指引中。
3. 使用 CHANGELOG 格式夾具，驗證報告能區分產物缺陷與規則、範本、閘門和測試層缺陷。
4. 對一個代表性的同類實例缺陷和一個代表性的控制面缺陷做變異檢查：重新引入缺陷時相關檢查必須失敗，恢復後必須通過。
5. 修改 payload 時打包 skill、INIT 一個臨時 Phase C 專案，驗證生成規則和 AGENTS 指引包含閉環協定且沒有 repo-only 路徑。
6. 執行適用的全倉庫閘門並記錄證據等級；不得聲稱新協定機械證明了語義正確性。
7. 分別執行一個 repo-infra 夾具和一個全新的 Phase C 被治理專案夾具，證明同一缺陷簽名在兩個域中都已閉環，或明確標記為不適用/阻塞。

## 完成條件

- 對觸發的治理缺陷，修復協定同時要求橫向同類閉環和縱向控制面閉環。
- 同一個觸發缺陷必須在 `repo-infra` 和被治理專案兩個域中都有明確結果；只修復報告所在一側不滿足完成條件。
- 修復協定有明確的範圍和停止條件。
- 至少一個目標專案夾具證明規則正確進入 payload。
- 至少一個有界負向檢查證明相關執行層不是空轉。
- 沒有未經獨立裁定就新增通用相似度引擎、萬能註冊表或寬泛閘門。
