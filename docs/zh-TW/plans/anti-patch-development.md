# 反補丁式開發與測試架構治理（TASK 計劃）

[English](../../en/plans/anti-patch-development.md) · [簡體中文](../../zh-CN/plans/anti-patch-development.md) · [繁體中文](anti-patch-development.md)

> **Status: design plan, not implemented.**（設計計劃，未實作。）本計劃治理 AI 在反覆打補丁、局部修復與失敗重試中的行為，不把「檔案行數」本身當作品質標準。

**Target：both** —— `payload` 增加根因修復、失敗升級與回歸證據規則；`repo-infra` 拆分測試架構、增加債務偵測、記錄指標並補齊測試。兩個域分別列在「受影響檔案」中。

### 任務目的

降低 AI 透過局部補丁暫時壓低測試失敗、卻不斷累積屎山與回歸缺陷的機率，使「修復一次」變成可重現、可解釋、可驗證的變更閉環。

### 當前問題

- AI 傾向圍繞最後一個錯誤做最小文字修改，缺少「重現 → 假設 → 根因 → 修復 → 回歸」的強制閉環。
- 同一個 bug 可以連續嘗試三、四次，每次只增加相容分支、特殊判斷或測試例外，卻沒有在失敗後升級為重新理解架構或請求審查。
- `tests/run-tests.js` 逐漸成為兩千行以上的單體測試檔案；測試註冊、fixture、執行器與斷言混在一起，導致模型更容易複製既有模式並繼續打補丁。
- 失敗測試經常沒有證明「修復前會失敗」，回歸測試可能只是覆蓋當前補丁，而沒有鎖定原始不變量。
- 當前變更衛生規則要求清理殘留，但沒有把重複失敗、補丁債務、測試單體化與未驗證假設轉成可審查的交付證據。

### 提議方案

#### 1. 增加根因修復協定

在每個中大型 bug 或機制變更的 TASK 計劃中增加：重現命令、預期失敗、根因假設、影響面、修復不變量、回歸測試與未決風險。實作前必須讓回歸測試在修復前失敗；如果無法重現，任務只能保持 `blocked` 或 `design plan, not implemented`，不得以猜測性補丁宣稱完成。

第一次成功重現時建立任務級 `repairSessionId`，後續所有修復嘗試都綁定該 ID；失敗簽名只作為輔助資訊，不能透過修改錯誤文字重置嘗試次數。每次嘗試記錄唯一編號、修改範圍、驗證結果與失敗原因。只有開發者明確裁定為新問題，才能結束當前會話並建立新的 ID。記錄只保存技術摘要，不複製秘密或整段對話。

#### 2. 設定失敗嘗試預算與升級規則

- 第一次失敗：停止繼續加補丁，重新檢查重現、呼叫鏈與架構邊界。
- 第二次失敗：必須擴大影響面搜尋並執行 review-manager，或取得開發者明確決定後改變假設。
- 第三次失敗：停止當前實作路徑，重新建立計劃；不得繼續堆疊相容分支、測試豁免或特殊 case。

「嘗試次數」按同一 `repairSessionId` 計數；失敗簽名與 diff 相似度只能輔助分組，不能作為重置依據。只有開發者明確批准「這是新問題」才能重置會話。成功標準是原始回歸測試、完整閘門與相關不變量通過，不是「最後一次命令變綠」。

#### 3. 拆分測試架構，保留穩定入口

保留 `npm test` 與 `node tests/run-tests.js` 作為相容入口，但將 `tests/run-tests.js` 收斂為測試發現、公共 runner 與彙總出口；按領域拆分到 `tests/suites/`，例如 validator、generator、policy、docs、release、payload。公共 fixture 與斷言輔助函式進入明確命名的測試支援模組。

拆分採用基線遞減策略：先保持測試行為與輸出不變，再分批遷移；不以機械行數閾值阻斷既有基線，只阻止新程式碼繼續擴大單體檔案，並在每次遷移後保留領域級可執行入口。遷移必須是單向的：測試遷入 `tests/suites/` 後從舊單體檔案刪除，舊檔案只保留 runner，不保留第二套測試註冊或實作；CI 與本地命令始終使用唯一的測試發現入口。遷移前後的測試 ID、數量與結果必須對帳。

#### 4. 增加低風險快速路徑

按影響面而不是行數決定是否簡化：純文件/拼寫/格式變更可走簡化流程；單檔案且無行為變更的修改允許一次快速修復；執行期、設定、權限、資料格式與公共介面問題，即使只改一行，也必須有重現與回歸測試。熱修復可以先恢復服務，但必須補齊回歸證據並在後續任務關閉補丁債務。快速路徑仍受第一次失敗重新理解、第二次失敗升級的規則約束。

#### 5. 把品質不變量寫成閘門

新增或擴展檢查，覆蓋：

- 回歸測試必須對應一個可重現的失敗場景或不變量；
- 回歸測試必須在修復前失敗、修復後通過；刪除修復後應重新失敗，或由邊界測試證明修復作用；
- 新增測試必須歸屬一個領域 suite，禁止繼續把測試無說明地堆入 runner；
- 測試檔案超過基線或單個 suite 異常膨脹時先報告，超過約定增長預算才阻斷；
- 當前層不得殘留已被替換的舊事實、臨時相容分支、無 owner 的 TODO 或測試豁免；
- 同一 `repairSessionId` 內連續失敗的修復嘗試必須有升級記錄，缺失時不能宣稱完成；
- 根因假設必須包含可反證的因果說明，不能只檢查欄位是否填寫。

檢查器只驗證結構與證據存在，不把「有測試」誤判為根因已經正確，也不自動判斷語義品質。

#### 6. 建立補丁債務報告

將重複修改路徑、重複失敗簽名、臨時分支、測試豁免、未決相容項與單體測試增長彙總到審查報告或 `.governance/drift-report.json`。報告區分當前層、過渡層與歷史層，避免把 CHANGELOG/ADR 中的歷史記錄誤報成殘留實作。

補丁債務達到閾值時，下一次相關任務自動提升為中/大型任務；涉及公共介面、資料格式或跨模組修復時強制 review-manager。

#### 7. 接入生命週期與 release gate

把根因修復協定放入 lifecycle 的 Understand/Plan/Validate/Report；把失敗升級與測試架構規則寫進生成的 AGENTS.md。日常檢查報告債務，發布前檢查阻斷未關閉的高風險項、stale 失敗記錄、未歸屬測試與未完成遷移。

本計劃不允許透過降低測試覆蓋、刪除失敗用例、擴大全域豁免或製造假 fixture 來「修復」閘門。

### 受影響檔案

#### Payload

- `references/policies/lifecycle.policy.md` —— 增加根因修復協定、失敗嘗試預算、升級規則與報告要求
- `references/policies/coding.policy.md` —— 定義補丁債務、臨時分支、測試豁免與根因不變量規則
- `references/templates/agents-md.template.md` —— 生成 Agent 可執行的修復協定與升級提示
- `references/workflows/release.md` —— 接入高風險補丁債務與未決失敗記錄的發布閘門
- `references/init-spec.json` —— 宣告新增報告/檢查工件（如最終決定複製進被治理專案）
- `SKILL.md` —— 更新 INIT/AUDIT/RELEASE 的修復閉環與升級邊界

#### 倉庫基礎設施

- `tests/run-tests.js` —— 保留相容入口並遷移為 runner/彙總出口
- `tests/suites/**` —— 按領域拆分現有測試
- `tests/support/**` —— 集中 fixture、runner 輔助與通用斷言
- `scripts/check-coding-hygiene.js` —— 增加補丁債務、測試歸屬與殘留證據檢查（若現有計劃已交付則擴展該腳本，不重複建立同類閘門）
- `scripts/check-doc-consistency.js` —— 檢查修復協定與同步文件標記
- `scripts/check-doc-freshness.js` —— 報告失敗記錄與測試文件的過時狀態（如適用）
- `tests/fixtures/**` —— 提供「修復前失敗、修復後通過」的最小回歸場景
- `docs/{en,zh-CN,zh-TW}/commands.md` —— 說明 review-manager 與根因修復流程的觸發方式
- `CHANGELOG.md` —— 在行為變化的發布邊界記錄閘門與測試架構變化

### 風險與決定

- 失敗預算可能促使 Agent 過早升級；因此第一次失敗只要求重新理解，第二次失敗才強制擴大審查，第三次失敗才停止當前路徑。`repairSessionId` 必須綁定任務，避免透過修改錯誤文字繞過預算。
- 行數閾值容易變成形式主義；採用「既有基線 + 增長預算 + 領域歸屬」而不是全域硬性 2000 行規則。
- 測試拆分本身可能產生大規模噪聲；先保持入口、輸出與測試語義不變，再按領域漸進遷移。
- 雙入口並存會造成動態漂移；遷移期間只能保留一個測試發現入口，舊單體檔案不再接受新測試。
- 根因欄位可能被偽造得很完整；因此必須要求修復前失敗、修復後通過和反證/邊界證據，並在第二次失敗時升級人工審查。
- 快速路徑可能被濫用於繞過行為驗證；路徑按影響面分類，執行期和設定故障不因修改行數少而豁免。
- 根因、遷移是否充分與補丁是否真正簡化仍需人工判斷；閘門只證明證據、結構與回歸執行結果。
- 不把每一次小修都強制升級成完整審查；只有重複失敗、高風險介面或跨模組變更觸發 review-manager。
- 本計劃與 consent/change-hygiene 計劃互補：前者治理「是否得到授權、刪除/重命名是否有證據」，本計劃治理「是否在錯誤反饋迴路中持續堆補丁」。

### 驗證方法

- 構造一個第一次修復失敗的 fixture，確認報告要求重新檢查假設而不是繼續寫補丁。
- 構造同一 `repairSessionId` 連續兩次失敗的場景，確認觸發 review-manager/開發者升級；修改錯誤文字不能重置計數，第三次失敗確認當前路徑被阻斷。
- 驗證只有開發者明確裁定為新問題時才能建立新的修復會話。
- 將 `tests/run-tests.js` 遷移為 runner 後，`npm test`、直接入口與領域 suite 的結果保持一致；舊檔案新增測試時閘門失敗。
- 驗證回歸測試修復前失敗、修復後通過，刪除修復後重新失敗或邊界測試能夠證明修復作用。
- 刪除或繞過回歸測試、增加無 owner 的豁免、把測試放入未登記領域時，閘門失敗並指出證據缺口。
- 驗證測試單體檔案只按新增增長預算治理，既有歷史基線不會一次性阻斷整個專案。
- 驗證當前層、過渡層、歷史層的補丁債務報告分類正確，不把 CHANGELOG、ADR、archive 的記錄誤判為程式碼殘留。
- 完成 payload 自包含檢查、三語文件 parity、`npm test`、`npm run check` 與 `npm run check:all`。
