# PLAN-0029：治理缺陷闭包

> （已归档。归档即断言完成。）（原状态：已实现，待 Release 归档。）同类实例闭包与控制面追查已写入根因修复协议，并经目标链路验证到达被治理项目。

**Target: both** —— `payload` 修改被治理项目收到的修复协议；`repo-infra` 更新 skill 执行指针、生成指引、目标链路测试、CHANGELOG，以及本计划/路线图索引。

## 本计划必须解决的两个原始问题

### 问题一——修复一个实例，却不排查同类实例

发现一个有缺陷的规则、模板、脚本、门禁、测试、发布条目、生成产物或同步文档后，Agent 往往只修复当前行，不搜索共享同一契约的其他实例。

计划必须要求在相关同类表面进行有界搜索，并写明搜索范围和命令或枚举方式；“没有发现其他问题”本身不算证据。

### 问题二——修复输出，却不追查控制面

Agent 可能只修复缺陷的可见输出或投影，却不检查产生或漏检它的规则、模板、生成器、门禁、测试预言机、发布流程或目标投影。因此问题可能再次出现，或在下一次生成时被覆盖。

计划必须要求检查相关控制面链路，同时覆盖源到输出和输出到消费者两条路径。

这两个问题属于同一类失败：局部修复在影响面和生产链检查完成前就停止。

## 工程克制边界

计划不新增通用相似度引擎、万能审计注册表、强制五层表格、新门禁或新状态体系。继续使用现有的 `repairSessionId`、影响面搜索、变更卫生对账和 `mutation-probe.js`。

## 提议方案

### 1. 双域对称（写入 `lifecycle.policy.md` 根因修复协议）

治理缺陷往往同时活在两个域——编写规则的一侧和执行规则的一侧。只修复被报告的那一侧、默认另一侧正确，是已被多次证实的漏修模式。

- 缺陷出现在项目自身的规则/脚本/门禁 → 必须检查它的来源与投影：生成该文件的模板或生成器、对应的检查器、以及规则文本本身是否也带同一错误。
- 缺陷出现在生成产物或分发产物 → 必须检查产生它的源文件与分发链路，不能只改产物（下次生成会覆盖）。
- 对应域不存在或不适用时必须写明具体原因，不得默认正确、不得静默略过。

### 2. 同类实例闭包

当缺陷属于治理契约而不是孤立措辞错误时，Agent 必须在声明的相关表面枚举同类实例后再完成。搜索范围可包括：

- 同一目录、脚本族、硬编码枚举或同步文档集合；
- 源规则、模板、生成器、生成投影和兼容层；
- repo-infra 与被治理项目的对应实现；
- 同一批次修改的相关文件。

每个表面必须给出简短结果：已修复、有证据证明正确、不适用并说明原因，或因前置条件缺失而阻塞。结果记录在现有 `repairSessionId` 中，不新增注册表。

### 3. 控制面追查

Agent 必须检查与缺陷相关的生产链和执行链，不能盲目执行无关清单。对于格式或输出缺陷，通常包括：

```text
权威规则 → 模板/生成器 → 输出
→ 检查器/门禁 → 测试预言机 → 发布或目标消费者
```

对于 payload 缺陷，还必须检查 tarball → INIT → 干净目标项目。对于 repo-only 缺陷，目标消费者可以是本仓库的发布或开发流程。每个相关层都必须修复、用证据证明正确，或明确标记为阻塞/不适用。

任何可见输出缺陷都不能只编辑输出文件。必须识别并检查适用的权威规则、产生路径、执行路径、证据路径以及发布或目标消费者边界；不适用的层必须明确说明理由。

### 4. 有界负向验证

当某个门禁/检查器声称能拦截该缺陷时，用一次有界的负向验证证明它不是空转：在隔离夹具中重新注入缺陷 → 该检查必须失败；恢复正确形式 → 必须通过。只对可判定的门禁行为要求，不要求语义判断做变异。

已有 `mutation-probe.js` 可承载此项，不新增机制。

### 5. 适用域与停止条件

本计划只适用于治理规则、模板、生成器、门禁、测试、生成产物、同步治理文档与发布流程；普通业务代码与孤立措辞错误不触发。

相关同类表面都有证据结果、相关控制面已检查、对应域已检查，并记录适用的回归/门禁证据后即可停止。

### 6. 本次明确不新增

- 通用相似度引擎
- 万能审计注册表
- 强制五层审查表
- 仅为本协议新增的门禁或审计脚本

## 与现有协议的关系

- 现有 `repairSessionId`、先复现字段和失败预算仍是会话与升级机制。
- 本要求补充而不是替代影响面搜索和变更卫生对账。
- 同类实例与控制面结论记录在现有修复会话中，不引入新的注册表或升级步骤。
- `mutation-probe.js` 是现有工具，本条仅为使用它的场景增加一条触发条件。

## 验证方法

1. 三语 parity 和计划状态门禁通过。
2. 夹具证明发现一个同类实例后，相关同类搜索能报告另一个实例；不新增相似度引擎。
3. 输出或投影夹具证明报告会检查适用的权威规则、产生路径、执行路径、证据路径以及发布/目标消费者边界，而不只检查输出。
4. payload 修改通过 tarball → INIT → 干净目标项目验证。
5. 门禁声称能捕获该缺陷时，使用 `mutation-probe.js` 或其他已有的有界检查，证明重新注入会失败、恢复后会通过。
6. `npm run check` 全绿。

## 完成条件

- repo-infra 与被治理项目的执行路径都能读到同一要求。
- 触发缺陷不能只修复可见输出或单一域后就声明完成。
- AGENTS.md 原则指针指向该文件。
