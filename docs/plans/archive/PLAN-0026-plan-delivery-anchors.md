# PLAN-0026：交付锚点

归档共享单语原文(简体中文为准)。原三语版本已随归档移除;本文件随 v0.14.0 归档于 2026-09-06。

> （已归档。归档即断言完成。）（原状态：已实现。）于 v0.13.2+（2026-09-06）交付：交付门禁新增锚点语法（`— anchor: `snippet``）；带锚点的已存在路径按**内容**验证，而非仅存在性。与计划的偏差（刻意）：未实施冻结基线清单——严格从当日起的锚点要求取代它，因计划自身 Risks 节警告「大冻结清单会从发布日起弱化规则」。两个回归测试 + 变异验证。见 CHANGELOG（边界拆分批次）。

**Target：repo-infra** —— 交付门禁与其测试属仓库基础设施，声明规范落在 `AGENTS.md`。本计划不产出任何进入被治理项目的内容。

### 任务目的

让交付门禁验证声明的内容真的落进了声明的文件。计划指名一个落地点，就要指明落地的是什么，门禁要能找到它。

### 当前问题

- 门禁验证声明路径的方式是查文件是否存在。对树中本就存在的文件，存在性在计划写下之前就已满足，于是无论计划承诺了什么，检查都报成功。
- 本次会话实例：`removal-hygiene` 声明了 `AGENTS.md` 与 `SKILL.md` 两个落地点，两个文件都没拿到那条规范。门禁报 28 plans verified，exit 0。缺口是人工通读发现的——而这正是门禁本该替代的那道保障。
- 行为声明（`writes:` / `wires:`）确实验证内容，但计划要主动采用该语法才享有验证。最可能不采用的，恰恰是用散文声明普通文件的普通计划。
- 覆盖面因此是反的：新建文件的计划被严格检查，改动既有治理文件的计划被空洞检查——而本仓库多数计划做的就是改动既有治理文件。

### 提议方案

- **锚点要求**：Affected Files 中若声明的路径早于本计划存在，则该条附带锚点——本次改动写入该文件的一小段引用文本。`AGENTS.md` —— 锚点：`删除即删净`。门禁在目标文件中搜锚点，找不到即失败。
- **先后判定**：比较声明路径的新增提交与计划文档的新增提交（`git log --diff-filter=A -1`）。路径新增更早，或计划尚未提交，则判定路径早于计划，需要锚点；路径由本计划引入，则存在性仍是有效证据。
- **基线豁免**：本规范之前写就的计划记入门禁脚本内的冻结清单，要求只对清单之外的计划生效。测试断言该清单不被追加，新计划无法混入。
- **无 git 兜底**：拿不到 git 元数据时，门禁把既有路径判为早于计划，并以咨询方式报告锚点要求而非直接失败，使检查在仓库导出副本中仍可运行。
- **规范落地**：AGENTS.md 中关于计划声明的规则，在既有 Target 字段规则旁增加锚点要求。

### 受影响文件

- repo-tools/check-plan-delivery.js —— 锚点解析、先后判定、冻结基线
- tests/suites/*.test.js —— 覆盖下列验证场景的回归(run-tests.js 只是发现入口;在其中注册测试会使卫生门禁失败)
- AGENTS.md —— 计划声明规范中的锚点要求
- CHANGELOG.md —— 门禁行为变更

### 风险

- **迁移量**：归档计划普遍声明既有文件，基线正是用来吸收它们的。选定切分点前先量出数量——冻结清单一旦很大，规则从上线当天就是弱的。
- **锚点漂移**：措辞日后被改写，锚点即失效，健康的树上门禁也会变红。锚点优先取稳定术语；锚点失效按修正计划处理，而非给门禁开豁免。
- **git 依赖**：先后判定读取仓库历史；兜底让门禁在历史不可得处降为咨询，而那恰恰是计划被四处复制的环境，验证强度在那里最弱。

### 验证方法

- 复现 `removal-hygiene` 场景：计划声明既有文件且无锚点，门禁转红并指名该计划。
- 锚点存在于目标文件则通过；锚点缺失则失败并指名该锚点。
- 由计划自身新建的路径仍靠存在性通过，确认对 `references/templates/githooks-template.md` 不产生误报。
- 冻结基线测试在清单被追加时失败。
- `npm run check` 与 `npm run check:all` exit 0，测试数上调。
