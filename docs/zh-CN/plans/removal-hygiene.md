# 变更归位与残留清理（TASK 计划）

[English](../../en/plans/removal-hygiene.md) · [简体中文](removal-hygiene.md) · [繁體中文](../../zh-TW/plans/removal-hygiene.md)

> **状态：已实现（2026-08-30，待 Release 归档）。** 本计划已在当前工作树交付；发布时按仓库规则归档。
>
> **Target: both** —— `payload` 交付给被治理项目（`SKILL.md`、`references/`）；`repo-infra` 维护本仓库的 `AGENTS.md`、测试和开发者文档。两类交付点分列在“受影响文件”中。
>
> **目标版本：v0.11.0（暂定）**。这是面向 Agent 的行为规则；若最终只做文档整理，发布时由 Release Proposal 按 SemVer 重新判定。实现阶段不直接改版本或创建发布。

### 任务目的

建立一条跨变更类型的**变更归位与残留清理规则**：修改完成后，当前规范层和当前实现层只表达现行事实；兼容/迁移信息进入明确的过渡层；变更原因和历史事实进入历史层。这样删除、重命名、迁移、替换或拆分合并后，后续 Agent 不会被过时的词、链接、配置、示例或相互矛盾的描述误导。

“删除即删净”是其中一种情况，不是完整规则。规则必须同时保护代码、配置、测试、CI、模板、生成物和三语文档之间的语义一致性。

### 当前问题

- 原计划只覆盖删除/替换后的否定式注脚，未覆盖重命名、移动、弃用、迁移、拆分、合并、关闭 feature flag 或修改 API/数据格式后的残留。
- “用旧名称全仓搜索，命中数必须为零”过于粗糙：CHANGELOG、ADR、归档计划、迁移指南、兼容别名和兼容测试可能必须保留旧名称；真正需要清零的是当前规范层中未获批准的残留。
- 只改单一事实源而不更新引用、锚点、动态加载名、环境变量、测试 fixture、生成物或翻译，会产生“代码已变、治理仍旧”的漂移。
- 删除公开接口、配置或数据格式时，如果没有调用方盘点、迁移方案、兼容窗口和回滚条件，容易把清理误做成无意的破坏性变更。
- 本次会话的具体旧内容、影响面和可接受兼容范围必须以实际搜索结果为准，不能由 Agent 凭印象判断“已经删干净”。

### 术语与分层

所有命中都先按所在表面分类，再判断是否为残留：

| 表面 | 内容 | 允许提及旧内容吗？ |
| --- | --- | --- |
| **当前规范/实现层** | 当前 `AGENTS.md`、`docs/rules/**`、当前架构/功能/命令文档、代码、配置、schema、CI、测试和 Agent 实际读取的生成物 | 默认不允许；只能保留仍然工作的兼容行为或必要的迁移指针 |
| **兼容/过渡层** | deprecation/migration 文档、兼容别名、adapter、feature flag 过渡逻辑、兼容测试、版本迁移说明 | 可以，但必须写明用途、范围、责任人和移除条件/版本；不得让旧内容看起来仍是首选行为 |
| **历史层** | `CHANGELOG.md`、ADR、`docs/archive/`、已完成计划的历史记录 | 可以；这里记录事实、原因和决策，不作为当前执行规则 |
| **计划/审查层** | 未完成计划、审查报告、任务报告 | 可以用于描述问题和验收，但不得被误当作运行期规则；完成后按归档规则保留历史 |

因此，判断标准不是“旧词在仓库中出现次数为零”，而是：**当前层没有未解释、未批准、会误导执行的旧事实；兼容层的每个例外都有明确的退出条件；历史层的记录不被当前 Agent 当作指令。**

### 适用的变更类型

| 变更类型 | 必须检查 | 旧内容的默认处理 |
| --- | --- | --- |
| 删除/移除 | 引用、导出、注册表、路由、配置、环境变量、文档、示例、测试、CI、生成物、链接和迁移影响 | 当前层清除；历史层保留原因；公开契约必须给出迁移或确认不需要迁移的证据 |
| 重命名/移动 | import、动态加载、插件名、路径、链接、锚点、命令触发词、配置键、环境变量、Feature/Architecture 登记和三语副本 | 当前层统一新名称；旧名仅在明确兼容别名或迁移说明中保留，并标记期限 |
| 替换/改写 | 新旧语义是否矛盾、单一事实源、示例、默认值、schema、测试断言和生成输出 | 当前层只描述新行为；旧行为说明进入迁移/历史层，不能用否定式注脚污染当前规则 |
| 弃用/软删除 | 首选新路径、兼容窗口、警告、责任人、移除版本、调用方通知和测试 | 旧内容可在兼容层存在；必须可识别为非首选，并有可执行的收口条件 |
| 拆分/合并/重组 | 归属、所有者、来源文件、交叉引用、目录索引、重复正文和同步组 | 当前层只保留一个权威来源；迁移映射放过渡层，避免两份正文继续分叉 |
| 关闭/移除配置或 feature flag | 默认值、schema、环境示例、CI、部署脚本、运行时分支、测试 fixture 和文档 | 明确是暂时关闭、弃用还是彻底移除；不能让已关闭能力看起来仍可用 |
| API/CLI/协议/数据格式变更 | 外部调用方、版本兼容、序列化、回滚、迁移脚本、release notes 和 SemVer | 无兼容方案不得静默删除；破坏性影响必须走高风险审查和发布判定 |
| 模板/生成物/翻译变更 | 源文件、生成文件、已有项目迁移、三语结构、链接和版本漂移 | 源头先定；生成物按明确流程更新；旧项目不因模板变更被静默覆盖 |
| 权限/安全/校验规则变更 | 保护范围、权限边界、失败闭环、回滚和用户确认 | 不能以“清理残留”为由放宽限制或移除门禁 |

### 提议方案

#### 1. 建立变更清单（Change Hygiene Ledger）

中/大型变更在计划的“受影响文件”之外，增加一张变更清单；小型单文件文档改动可在最终报告中使用精简版。每个被移除、改名、替换或迁移的概念/路径/接口都要有一行：

| ID | 类型 | 旧项 → 新项 | 影响表面 | 处理决定 | 允许旧引用/退出条件 | 证据 |
| --- | --- | --- | --- | --- | --- | --- |
| CH-01 | rename | `old` → `new` | code/docs/config | 全量改名，保留兼容别名至 vX | `docs/migration.md`；vX 移除 | `rg` + 测试 |

处理决定只能是 `remove`、`rename`、`replace`、`deprecate`、`retain` 或 `migrate`。没有决定、所有者、退出条件或证据的条目视为 `unresolved`，不能宣称完成。

#### 2. 变更前：发现影响面

在修改前，Agent 必须：

1. 记录旧名、旧路径、旧配置键、旧命令、旧 schema 字段、旧 feature 名和可能的动态字符串；不要只搜自然语言标题。
2. 使用 `rg` 搜索代码、配置、文档、测试、CI、模板、生成物和三语树；对插件、反射、字符串拼接、manifest、环境变量和脚本参数做额外检查。
3. 将每个命中放入当前层、兼容层、历史层或 `unresolved`；搜索命中的文件进入 Affected Files。
4. 先确定是“彻底移除”还是“兼容迁移”。如果存在公共调用方、动态引用或未知消费者，默认按高风险/阻塞处理，不能直接删除。

#### 3. 变更中：先改权威源，再收敛投影

- 先更新单一事实源，再同步 AGENTS 指针、规则文件、架构/Feature 登记、代码引用、配置、测试、CI、模板、生成物和翻译。
- 当前规范层只写现行行为；不要用“已删除”“不再支持”“这里曾经……”等注脚代替清理。若用户确实需要知道迁移方式，把说明放入兼容/迁移层并给出退出条件。
- 重命名或移动时，兼容别名、重定向、shim、adapter 必须是有意保留的条目，并在变更清单声明，不得因为“全仓零命中”被误删。
- 删除代码前仍必须遵守删除保护：说明原因、确认归属、搜索引用、检查 Feature Registry 影响、提供迁移/回滚方案；动态调用和配置驱动路径必须人工核验。
- 不把 CHANGELOG、ADR、归档计划中的历史描述复制回当前规则或正文；当前文档只引用规则源，不重复规则正文。

#### 4. 变更后：按表面做定向清理

验证分为四类，不再使用单一的“全仓命中数”：

- **当前层检查**：旧标识符、旧链接、旧锚点、旧配置键、旧命令和旧语义的未解释命中必须为零。
- **兼容层检查**：每个保留命中都在变更清单中有理由、范围、责任人、移除版本/日期和对应测试或迁移文档。
- **历史层检查**：CHANGELOG、ADR、归档和计划可以保留旧内容，但不得被当前 Agent 的执行路径引用成现行规则。
- **投影一致性检查**：代码/配置/测试/CI/模板/生成物/三语文档之间无断链、重复权威源或互相矛盾的说法。

任一命中无法分类、公共消费者无法确认、兼容边界未决定、生成物未更新或迁移/回滚未验证，任务标为 `⚠️ Blocked` 或 `❌ Failed`，不得用否定式注脚掩盖。

#### 5. 生命周期接入

- **Phase 1 Understand**：读取架构、Feature、规则和最近 CHANGELOG，识别变更类型与旧/新项。
- **Phase 2 Plan**：中/大型计划必须包含 Change Hygiene Ledger、兼容性决定、迁移/回滚方案、Affected Files 和 Target。
- **Phase 3 Implement**：按“权威源 → 引用 → 投影”顺序修改，逐项更新清单。
- **Phase 4 Validate**：运行当前层/兼容层/历史层/投影检查及标准测试、静态检查、构建和文档门禁。
- **Phase 5 Synchronize**：同步 CHANGELOG、ADR、Feature、Architecture、三语文档和计划状态；历史原因只写历史层。
- **Phase 6 Report**：报告已移除/改名/替换/弃用项、保留的兼容项及退出条件、未解决命中、迁移/回滚结果和真实验证证据。

这条规则适用于小型改动，但小型改动可以使用精简清单；涉及公共接口、权限安全、数据格式、跨模块重组或未知动态引用时，按大型改动执行并进行深度审查。

#### 6. 规则落点与迁移

实际规范正文放在 `references/policies/lifecycle.policy.md`（必要时由 `coding.policy.md` 添加指针），生成项目的 `docs/rules/` 由源文件复制；`SKILL.md` 和本仓库 `AGENTS.md` 只保留指针或摘要，不复制完整规则。

已有治理项目不会因源模板变化自动更新。明确升级时按 MIGRATE 流程合并生命周期/编码规则、Agent 摘要和相关生成物，保留已有兼容安排，并运行目标项目 validator；不得把一次清理任务偷偷变成全项目重构。

### 受影响文件

#### Payload（交付给被治理项目）

- `references/policies/lifecycle.policy.md` —— 作为变更归位与残留清理的权威规则，加入四层表面、Change Hygiene Ledger、变更矩阵、生命周期接入和验证标准
- `references/policies/coding.policy.md` —— 将 Code Modification / Deletion Protection 指向通用变更清单，并补充重命名、迁移、弃用和公共契约检查
- `references/templates/agents-md.template.md` —— 增加精简摘要/指针：变更前搜影响面、当前/兼容/历史分层、无未解释残留；不在模板复制完整矩阵
- `SKILL.md` —— 只增加指向权威 lifecycle/coding policy 的入口说明（不复制正文；若现有入口已足够则不改）

#### Repo-infra（本仓库维护）

- `AGENTS.md` —— 增加本仓库贡献者可执行的变更归位指针；遵守本仓库的 payload/repo-infra 分层，不重复规则正文
- `tests/run-tests.js` —— 增加当前层零残留、兼容层元数据、动态引用/链接、生成物/三语同步和迁移兼容的契约测试
- `docs/en/anti-regression.md`、`docs/zh-CN/anti-regression.md`、`docs/zh-TW/anti-regression.md` —— 更新开发者机制地图，说明该规则覆盖的变更类型
- `docs/en/lifecycle.md`、`docs/zh-CN/lifecycle.md`、`docs/zh-TW/lifecycle.md` —— 更新生命周期摘要，指向完整变更清单规则
- `docs/glossary.md` —— 如新增 Change Hygiene、compatibility surface、historical surface 等术语，先补三语词条
- `CHANGELOG.md` —— 在 `[Unreleased]` 记录行为变化（`Changed`）；不为每次业务清理单独创建版本条目

本计划的三语副本也必须同步。`docs/{en,zh-CN,zh-TW}/commands.md` 只有在新增/修改触发词或子技能时才加入；本计划本身不新增提示词。发布时按 Release 流程同步版本、归档计划和 roadmap，不在本计划实施阶段自动执行。

### 风险与缓解

- **规则过宽导致 Agent 不敢改动**：按变更类型分级；只阻断未分类、影响公共契约或涉及安全/权限的高风险项，小型明确改动使用精简清单。
- **全仓零命中误伤兼容/历史记录**：搜索仍覆盖全仓，但验收按当前、兼容、历史、计划四层分类；兼容例外必须有退出条件。
- **动态引用漏检**：把字符串、插件注册、manifest、环境变量、脚本参数和生成物列为强制搜索面；无法确认时阻塞，不假设没有消费者。
- **删除被错误改成破坏性变更**：公共 API/CLI/协议/数据格式必须有调用方盘点、迁移、回滚和 SemVer 判定。
- **多处权威源分叉**：先改源文件，再更新投影；AGENTS/SKILL/docs 只做摘要或指针，不能复制正文。
- **兼容层无限期残留**：每个别名、shim、旧配置和 deprecation 条目必须有责任人、移除版本/日期和测试；到期由后续清理任务处理。
- **安全门禁被“清理”掉**：权限、安全、删除保护和校验步骤的修改继续走治理文件保护及高风险审查，不能用本规则降低门槛。
- **三语/生成项目漂移**：源文档、三语文档和已有项目迁移分别验证；生成器不覆盖既有文件。

### 验收与验证方法

#### 自动/契约测试

- 变更清单能表达 `remove`、`rename`、`replace`、`deprecate`、`retain`、`migrate`，缺少决定或证据的条目不能标记为完成。
- 当前层的旧符号、旧路径、旧链接、旧锚点、旧配置和旧语义命中会被报告；CHANGELOG/ADR/归档中的合法历史命中不会被误报为残留。
- 兼容层命中缺少责任人、退出版本/日期、迁移说明或测试时会失败；有完整元数据时通过。
- 模拟删除、重命名、替换、弃用、feature flag 关闭、拆分合并、API/数据格式变更，分别验证引用、配置、测试、CI、生成物和文档同步。
- 动态字符串/插件注册/manifest/环境变量 fixture 能被发现；未知公共消费者或未分类命中进入 `Blocked`。
- 旧模板/旧 `state`/旧活动记录和既有治理项目通过 MIGRATE fixture 后仍可读取；已有文件不被自动覆盖。

#### Agent 行为验收（狗粮场景）

构造一组同时包含：删除一个内部文档段落、重命名一个配置键、保留一个带截止版本的兼容别名、弃用一个公开命令、移动一个生成模板的任务，检查：

1. Agent 在修改前输出旧/新项、影响表面、处理决定和 Affected Files。
2. 当前层只保留现行名称和行为；兼容层明确用途、责任人和退出条件；历史层保留原因；不添加“已删除/不再……”式当前注脚。
3. 未分类命中、动态引用不明或迁移未完成时不能宣称完成；状态和报告写明阻塞原因。
4. 重复运行不产生重复权威源；生成物和三语文档保持一致。
5. 若变更涉及公共契约或安全规则，出现单独的审查/确认记录、迁移或回滚证据和正确的版本分类。

#### 本仓库门禁

- 本仓库运行 `npm test`、`npm run check`；不运行或伪造默认 `scripts/verify_governance.js` 的通过结果。
- 修改 `references/`、脚本或三语文档后运行 `docs:parity`、`docs:layout`、`check-doc-consistency.js`，并记录真实输出。
- 用 `rg` 做一次影响面复核，将无法归类的命中逐项解释；用 `git diff --name-only` 对照计划 Affected Files 和 Target。
- 计划交付门禁通过后才可在发布流程归档；归档保留历史记录，不把历史说明复制回当前规范层。
