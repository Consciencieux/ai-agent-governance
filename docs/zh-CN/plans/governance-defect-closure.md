# 治理缺陷闭包——同类实例与控制面审查（TASK 计划）

[English](../../en/plans/governance-defect-closure.md) · [简体中文](governance-defect-closure.md) · [繁體中文](../../zh-TW/plans/governance-defect-closure.md)

> **Status: design plan, not implemented.** 本计划补充现有根因修复协议的缺口：修复被报告的实例，并不等于已经闭合同一缺陷类别，也不等于审查了允许该缺陷产生、传播或漏检的规则、模板、生成器、门禁、测试和发布链路。

**Target: both** —— `payload` 修改被治理项目 Agent 获得的修复协议；`repo-infra` 更新 skill 执行指针、生成的 Agent 摘要、目标链路测试、CHANGELOG，以及本三语计划/路线图索引。两类文件分别列在 Affected Files 中。

## 任务目的

让已确认的治理缺陷在缺陷族层面闭合，而不是只修复被报告的文件或行。修复必须同时覆盖两个维度：

1. **横向闭包** —— 枚举并处理同一缺陷签名的同类实例。
2. **纵向闭包** —— 检查产生、传播或未能发现该缺陷的控制面链路。

本计划只适用于治理行为、规则、模板、生成器、门禁、测试、发布记录和生成产物。不把普通拼写错误自动升级为全仓库审查。

## 适用域与双域对称

这是一个双域协议，同时适用于本 skill 仓库（`repo-infra`）和接收 payload 的被治理项目；只在其中一个域实现并不算完成。

- 首先在 `repo-infra` 发现的缺陷，必须检查对应的 payload 规则、模板、生成器、门禁、测试和目标项目投影。
- 首先在被治理项目发现的缺陷，必须检查本仓库中对应的源文件和分发链路。
- 对本仓库，`AGENTS.md` 和 skill 执行指引必须要求 Agent 执行闭包；对被治理项目，分发的生命周期规则、`SKILL.md` 和生成的 `AGENTS.md` 必须提出同样要求。
- 必须做反向检查：同时检查源到产物、产物到消费者的路径，包括生成产物和发布打包。

如果只修复一个域中的报告实例，却默认另一个对应域正确，则不得声称完成。

## 当前问题

现有根因协议已经要求复现、修复会话、失败预算和回归验证，但没有明确要求 Agent：

- 发现一个实例后搜索同一缺陷模式的全部实例；
- 同时检查权威规则、模板、生成器、门禁、测试和目标项目投影；
- 区分产物错误、规则错误、传播错误、执行错误和证据错误；
- 对本应捕获该缺陷的门禁重新注入缺陷，证明它确实会变红。

这会形成局部修复模式：

```text
报告实例 → 修复实例 → 命令变绿 → 宣布完成
```

要求的模式是：

```text
报告实例 → 缺陷签名 → 同类实例枚举
→ 控制面审查 → 修复全部适用表面
→ 负向/变异证据 → 目标环境验证
```

## 提议方案

### 1. 修复触发与缺陷签名

在根因修复协议中增加**闭包触发条件**。当已确认缺陷涉及规则、模板、生成器、门禁、测试、发布格式、生成产物、共享枚举或同一变更批次时触发。普通孤立措辞错误如果没有暴露更广泛的规则或投影问题，仍不在范围内。

闭包开始时记录简短的 `defect signature`，包括：

- 可观察到的失败；
- 被违反的不变量或契约；
- 可能产生其他实例的模式；
- 受影响的受众和执行环境；
- 必须枚举的搜索表面。

签名绑定现有的 `repairSessionId`，不新增第二个会话或注册表。

### 2. 横向闭包：同类实例

Agent 必须在所有可能承载该契约的表面上枚举同一签名：

- 同一目录、脚本、分支和硬编码枚举；
- 源规则、模板、生成器、生成投影和兼容层；
- payload 与 repo-infra 对应实现；
- 多语言投影和同步文档；
- 生命周期阶段和执行环境；
- 同一批次中修改的相关文件。

每个枚举到的实例必须明确给出一种结果：

```text
fixed
already correct（附证据）
not applicable（附原因）
blocked（附缺少的前置条件）
```

“没有找到其他匹配项”本身不算证据；报告必须写明搜索表面以及使用的命令或枚举方式。

### 3. 纵向闭包：控制面审查

治理缺陷必须检查完整控制面链路：

```text
权威规则
→ 模板/生成器
→ 实现或生成产物
→ 门禁/检查器
→ 测试预言机
→ 发布/归档流程
→ 目标执行环境
```

每一层都必须判断它属于：

- 缺陷来源；
- 传播该缺陷的路径；
- 本应捕获但没有捕获的执行缺口；
- 允许空洞绿灯的证据缺口；
- 已正确、无需修改的层。

例如 CHANGELOG 格式错误，不能只改 CHANGELOG。必须检查格式规则、生成的 AGENTS 指引、结构检查器、相关测试预言机、发布流程和生成后的被治理项目形态。

### 4. 证据与变异要求

现有证据等级继续作为权威：每个结论必须标注机械、人工背书或未验证。

当某个门禁、测试或检查器按设计应该发现该缺陷时，修复必须包含一个有界的负向检查：

```text
在隔离夹具中重新引入缺陷 → 检查应失败
恢复正确形式 → 检查应通过
```

这只适用于可判定的门禁行为，不要求每个语义判断都做变异，也不引入通用 mutation testing 框架。

### 5. 范围与停止条件

只有满足上述触发条件时才要求闭包扫描。满足以下条件即可停止：

- 缺陷签名已在声明的搜索表面上完成枚举；
- 每个适用实例都有结果；
- 每个失败的执行层都已修复，或明确标记为 blocked；
- payload 变更已在目标环境检查；
- 原始回归和相关门禁在负向检查后通过。

不得添加通用相似度引擎、万能审计注册表，或仅为记录清单而新增通用门禁。将来某类缺陷反复出现且可机械判定时，再通过独立计划增加窄范围门禁。

## 与现有协议的关系

- 现有 `repairSessionId`、先复现字段和失败预算仍是会话与升级机制。
- 闭包要求补充 impact-face 搜索和变更卫生对账，不替代它们。
- 现有失败预算后的 review-manager 升级仍然有效；闭包不能绕过开发者裁定或确认边界。
- 绿色门禁仍只有其声明的证据等级；闭包不能把机械证据升级为语义正确性声明。

## Affected Files

**payload：**

- `references/policies/lifecycle.policy.md` —— 在根因修复协议中增加闭包触发、缺陷签名、横向同类闭包、纵向控制面审查和有界负向检查要求
- `SKILL.md` —— 将 AUDIT 和修复编排指向闭包协议，防止 skill 执行器停在报告实例
- `references/templates/agents-md.template.md` —— 如果生成的 AGENTS 契约需要操作性指针，则携带面向被治理项目的修复摘要

**repo-infra：**

- `tests/suites/payload.test.js` —— payload 契约修改后，验证闭包条款进入干净的 Phase C 目标项目
- `AGENTS.md` —— 如果实现后的规则成为本仓库的持久治理原则，增加纯指针原则索引条目
- `CHANGELOG.md` —— 在发布边界记录 payload 行为变更
- `docs/{en,zh-CN,zh-TW}/plans/governance-defect-closure.md` —— 本计划
- `docs/{en,zh-CN,zh-TW}/roadmap.md` —— 在适当路线图阶段链接活跃计划

本计划不包含通用缺陷注册表、相似度引擎或万能门禁。

## 风险与裁定

- **范围膨胀：** 缺陷签名可能写得过宽。缓解：要求命名搜索表面和触发条件；普通文档改动仍不触发。
- **仪式化闭包报告：** Agent 可能列出表面却没有检查。缓解：要求真实命令输出或明确人工背书/未验证标记，并要求门禁类缺陷提供负向检查。
- **过度测试：** 每个可能变异都运行会重新制造过重机制。缓解：每个受影响执行契约只做一个有界负向夹具。
- **载荷漂移：** 只改规则、不检查生成项目会重演“编写环境正确、执行环境错误”。缓解：payload 变更执行 tarball → INIT → 目标闭包链路。
- **责任未决：** 控制面层属于其他计划或责任人时，标记为 blocked 并写明前置条件，不得静默省略。

## 验证方法

1. 运行三语 parity 和计划状态门禁。
2. 实施时证明闭包触发存在于 skill 执行器和生成的被治理项目指引中。
3. 使用 CHANGELOG 格式夹具，验证报告能区分产物缺陷与规则、模板、门禁和测试层缺陷。
4. 对一个代表性的同类实例缺陷和一个代表性的控制面缺陷做变异检查：重新引入缺陷时相关检查必须失败，恢复后必须通过。
5. 修改 payload 时打包 skill、INIT 一个临时 Phase C 项目，验证生成规则和 AGENTS 指引包含闭包协议且没有 repo-only 路径。
6. 运行适用的全仓库门禁并记录证据等级；不得声称新协议机械证明了语义正确性。
7. 分别运行一个 repo-infra 夹具和一个全新的 Phase C 被治理项目夹具，证明同一缺陷签名在两个域中都已闭合，或明确标记为不适用/阻塞。

## 完成条件

- 对触发的治理缺陷，协议同时要求横向同类闭包和纵向控制面闭包。
- 同一个触发缺陷必须在 `repo-infra` 和被治理项目两个域中都有明确结果；只修复报告所在一侧不满足完成条件。
- 协议有明确的范围和停止条件。
- 至少一个目标项目夹具证明规则正确进入 payload。
- 至少一个有界负向检查证明相关执行层不是空转。
- 没有未经独立裁定就新增通用相似度引擎、万能注册表或宽泛门禁。
