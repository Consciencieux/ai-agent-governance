# 反补丁式开发与测试架构治理（TASK 计划）


> **Status: archived.**（已归档。归档即断言完成。）（已实现，待归档。已交付：§1 根因修复协议、§2 失败预算（`references/policies/lifecycle.policy.md`）、§3 测试架构拆分（`tests/suites/` + 单一发现入口）、§5 的机械子集（`scripts/check-coding-hygiene.js`）。§4 快速路径、§6 补丁债务报告、§7 release-gate 接线仍为设计，按机制测试各自单独举证后再落地。）本计划治理 AI 在反复打补丁、局部修复和失败重试中的行为，不把“文件行数”本身当作质量标准。

**Target：both** —— `payload` 增加根因修复、失败升级和回归证据规则；`repo-infra` 拆分测试架构、增加债务检测、记录指标并补齐测试。两个域分别列在“受影响文件”中。

### 任务目的

降低 AI 通过局部补丁暂时压低测试失败、却不断积累屎山和回归缺陷的概率，使“修复一次”变成可复现、可解释、可验证的变更闭环。

### 当前问题

- AI 倾向于围绕最后一个报错做最小文本修改，缺少“复现 → 假设 → 根因 → 修复 → 回归”的强制闭环。
- 同一个 bug 可以连续尝试三四次，每次只增加兼容分支、特殊判断或测试例外，却没有在失败后升级为重新理解架构或请求审查。
- `tests/run-tests.js` 逐渐成为两千行以上的单体测试文件；测试注册、fixture、执行器和断言混在一起，导致模型更容易复制已有模式和继续打补丁。
- 失败测试经常没有证明“修复前会失败”，回归测试可能只是覆盖了当前补丁，而没有锁定原始不变量。
- 当前变更卫生规则要求清理残留，但没有把重复失败、补丁债务、测试单体化和未验证假设转成可审查的交付证据。

### 提议方案

#### 1. 增加根因修复协议

在每个中大型 bug 或机制变更的 TASK 计划中增加：复现命令、预期失败、根因假设、影响面、修复不变量、回归测试和未决风险。实现前必须先让回归测试在修复前失败；如果无法复现，任务只能保持 `blocked` 或 `design plan, not implemented`，不得以猜测性补丁宣称完成。

第一次成功复现时建立任务级 `repairSessionId`，后续所有修复尝试都绑定该 ID；失败签名只作为辅助信息，不能通过修改报错文本重置尝试次数。每次尝试记录唯一编号、修改范围、验证结果和失败原因。只有开发者明确裁定为新问题，才能结束当前会话并建立新的 ID。记录只保存技术摘要，不复制秘密或整段对话。

#### 2. 设置失败尝试预算与升级规则

- 第一次失败：停止继续加补丁，重新检查复现、调用链和架构边界。
- 第二次失败：必须扩大影响面搜索并运行 review-manager，或取得开发者明确决定后改变假设。
- 第三次失败：停止当前实现路径，重新建立计划；不得继续堆叠兼容分支、测试豁免或特殊 case。

“尝试次数”按同一 `repairSessionId` 计数；失败签名和 diff 相似度只能辅助聚类，不能作为重置依据。只有开发者明确批准“这是新问题”才能重置会话。成功标准是原始回归测试、完整门禁和相关不变量通过，不是“最后一次命令变绿”。

#### 3. 拆分测试架构，保留稳定入口

保留 `npm test` 与 `node tests/run-tests.js` 作为兼容入口，但将 `tests/run-tests.js` 收敛为测试发现、公共 runner 和汇总出口；按领域拆分到 `tests/suites/`，例如 validator、generator、policy、docs、release、payload。公共 fixture 和断言辅助函数进入明确命名的测试支持模块。

拆分采用基线递减策略：先保持测试行为与输出不变，再逐批迁移；不以机械行数阈值阻断既有基线，只阻止新代码继续扩大单体文件，并在每次迁移后保留领域级可运行入口。迁移必须是单向的：测试迁入 `tests/suites/` 后从旧单体文件删除，旧文件只保留 runner，不保留第二套测试注册或实现；CI 和本地命令始终使用唯一的测试发现入口。迁移前后的测试 ID、数量和结果必须对账。

目录形状：`tests/support/`（tmp、write、git 辅助、fixture、公共断言）与 `tests/suites/{validator,security,docs,generator,release,consistency,payload}.test.js`（领域划分以迁移时实际区段归属为准，不机械套用清单）。迁移边界：不引入 Jest/Mocha 等新依赖；不为此创建复杂 fixture 框架；不要求每个 suite 有独立 CLI；先迁移一组并对账其测试名称、数量、结果与输出，再迁移下一组。执行模型保持现状：暂不切换 `node:test`——它是标准能力，但会引入执行模型、输出与兼容行为变化，当前自定义 runner 已能工作，职责拆分的收益更明确，待拆分完成后再评估。

batch-2 待办（尚未交付，故不列入受影响文件）：tests/support/ 收拢共享 helper（当前由 run-tests.js 的 global 注入承担）、tests/fixtures/ 最小回归场景。

时机：拆分不阻塞功能开发；下一次涉及测试结构的大改动、或 `tests/run-tests.js` 再增长约 200–300 行之前执行；不做一次性全量重写。测试文件本身不是测试失败根因——拆分改善可维护性，不替代对具体失败的单独修复。

#### 4. 低风险快速路径

按影响面而不是行数决定是否简化：纯文档/拼写/格式改动可走简化流程；单文件且无行为变化的改动允许一次快速修复；运行时、配置、权限、数据格式和公共接口问题，即使只改一行，也必须有复现与回归测试。热修复可以先恢复服务，但必须补齐回归证据并在后续任务关闭补丁债务。快速路径仍受第一次失败重新理解、第二次失败升级的规则约束。

#### 5. 把质量不变量写成门禁

新增或扩展检查，覆盖：

- 回归测试必须对应一个可复现的失败场景或不变量；
- 回归测试必须在修复前失败、修复后通过；删除修复后应重新失败，或由边界测试证明修复作用；
- 新增测试必须归属一个领域 suite，禁止继续把测试无说明地堆入 runner；
- 测试文件超过基线或单个 suite 出现异常膨胀时只先报告，超过约定增长预算才阻断；
- 当前层不得残留已被替换的旧事实、临时兼容分支、无 owner 的 TODO 或测试豁免；
- 同一 `repairSessionId` 内连续失败的修复尝试必须有升级记录，缺失时不能宣称完成；
- 根因假设必须包含可反证的因果说明，不能只检查字段是否填写。

检查器只验证结构和证据存在，不把“有测试”误判为根因已经正确，也不自动判断补丁的语义质量。

#### 6. 建立补丁债务报告

将重复修改路径、重复失败签名、临时分支、测试豁免、未决兼容项和单体测试增长汇总到审查报告或 `.governance/drift-report.json`。报告区分当前层、过渡层和历史层，避免把 CHANGELOG/ADR 中的历史记录误报成残留实现。

补丁债务达到阈值时，下一次相关任务自动提升为中/大型任务；涉及公共接口、数据格式或跨模块修复时强制 review-manager。

#### 7. 接入生命周期和 release gate

把根因修复协议放入 lifecycle 的 Understand/Plan/Validate/Report；把失败升级和测试架构规则写进生成的 AGENTS.md。日常检查报告债务，发布前检查阻断未关闭的高风险项、stale 失败记录、未归属测试和未完成迁移。

本计划不允许通过降低测试覆盖、删除失败用例、扩大全局豁免或制造假 fixture 来“修复”门禁。

### 受影响文件

#### Payload

- `references/policies/lifecycle.policy.md` —— 增加根因修复协议、失败尝试预算、升级规则和报告要求
- `references/policies/coding.policy.md` —— 定义补丁债务、临时分支、测试豁免和根因不变量规则
- `references/templates/agents-md.template.md` —— 生成 Agent 可执行的修复协议与升级提示

- `references/init-spec.json` —— 声明新增报告/检查工件（如最终决定复制进被治理项目）
- `SKILL.md` —— 更新 INIT/AUDIT/RELEASE 的修复闭环和升级边界

#### 仓库基础设施

- `tests/run-tests.js` —— 保留兼容入口并迁移为 runner/汇总出口
- `tests/suites/**` —— 按领域拆分现有测试
- `scripts/check-coding-hygiene.js` —— 增加补丁债务、测试归属和残留证据检查（若现有计划已交付则扩展该脚本，不重复创建同类门禁）
- `scripts/check-doc-consistency.js` —— 检查修复协议和同步文档标记
- `scripts/check-doc-freshness.js` —— 报告失败记录和测试文档的过时状态（如适用）
- `docs/{en,zh-CN,zh-TW}/commands.md` —— 说明 review-manager 与根因修复流程的触发方式
- `CHANGELOG.md` —— 在行为变化的发布边界记录门禁和测试架构变化

### 风险与决定

- 失败预算可能促使 Agent 过早升级；因此第一次失败只要求重新理解，第二次失败才强制扩大审查，第三次失败才停止当前路径。`repairSessionId` 必须绑定任务，避免通过改错误文本绕过预算。
- 行数阈值容易变成形式主义；采用“既有基线 + 增长预算 + 领域归属”而不是全局硬性 2000 行规则。
- 测试拆分本身可能产生大规模噪声；先保持入口、输出和测试语义不变，再按领域渐进迁移。
- 双入口并存会造成动态漂移；迁移期间只能保留一个测试发现入口，旧单体文件不再接受新测试。
- 根因字段可能被伪造得很完整；因此必须要求修复前失败、修复后通过和反证/边界证据，并在第二次失败时升级人工审查。
- 快速路径可能被滥用于绕过行为验证；路径按影响面分类，运行时和配置故障不因改动行数少而豁免。
- 根因、迁移是否充分和补丁是否真正简化仍需人工判断；门禁只证明证据、结构和回归执行结果。
- 不把每一次小修都强制升级成完整审查；只有重复失败、高风险接口或跨模块变更触发 review-manager。
- 本计划与 consent/change-hygiene 计划互补：前者治理“是否得到授权、删除/重命名是否有证据”，本计划治理“是否在错误反馈回路中持续堆补丁”。
- 与工程克制原则（Engineering Restraint）的关系：本计划是工程克制在修复域的具体适用。新增或扩展反补丁机制时，先遵循其机制测试；已批准的反补丁协议不因其复杂而被 Agent 自行删减；冲突或必要性不明确时必须升级，不得本地裁决。各项机制在实现时各自单独举证（解决哪个当前问题、不用它的具体损失、是否已有机制可承载、是否最窄方案），不以单一证据捆绑获批。机制必要性裁决记录在 TASK 计划或审查结论中——`repairSessionId` 自身实现并获批前，不作为记录位置。

### 验证方法

- 构造一个第一次修复失败的 fixture，确认报告要求重新检查假设而不是继续写补丁。
- 构造同一 `repairSessionId` 连续两次失败的场景，确认触发 review-manager/开发者升级；修改错误文本不能重置计数，第三次失败确认当前路径被阻断。
- 验证只有开发者明确裁定为新问题时才能建立新的修复会话。
- 将 `tests/run-tests.js` 迁移为 runner 后，`npm test`、直接入口和领域 suite 的结果保持一致；旧文件新增测试时门禁失败。
- 验证回归测试修复前失败、修复后通过，删除修复后重新失败或边界测试能够证明修复作用。
- 删除或绕过回归测试、增加无 owner 的豁免、把测试放入未登记领域时，门禁失败并指出证据缺口。
- 验证测试单体文件只按新增增长预算治理，既有历史基线不会一次性阻断整个项目。
- 验证当前层、过渡层、历史层的补丁债务报告分类正确，不把 CHANGELOG、ADR、archive 的记录误判为代码残留。
- 完成 payload 自包含检查、三语文档 parity、`npm test`、`npm run check` 和 `npm run check:all`。
