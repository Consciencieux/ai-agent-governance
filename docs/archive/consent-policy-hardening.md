# Consent 政策重写：提交前一次确认（TASK 计划）

> **Status: archived.**（已归档。归档即断言完成。）

**Target：both** —— 五个同步点：本仓库侧 `AGENTS.md`；载荷侧 `references/policies/git.policy.md`（权威详解）、`references/policies/lifecycle.policy.md`（Phase 2 确认门）、`references/templates/agents-md.template.md`（被治理项目模板摘要）、`SKILL.md`（权限矩阵）。改任何一处必须同步其余四处，同步点清单见「受影响文件」。

### 任务目的

清除三层补丁屎山，把确认政策从"每步确认 + 例外补丁"重构为单一原则——**提交前回显完整 git 命令序列，确认一次后执行**。用户说 push 后，展示将要执行的 add 文件清单、commit 消息（类型含在消息前缀）、push 目标分支，用户确认一次即执行完。计划批准降级为意图对齐；规模分级降级为决定是否写计划文档。政策曾被其作者多次违反（本会话真实事故），重写目标是一次清掉旧框架，不留补丁。

### 当前问题

- 三层补丁叠床架屋：主规则"每次 Git 写操作当轮独立确认"之上，先打 release 序列例外（v0.9.1），再打用户显式指令例外 A（本会话），还发生过漏改同步点后补（SKILL.md 例外二）。规则总数在增长，语义在互相打架。
- 两个政策各自规定确认：一般更改政策按"计划"确认（lifecycle Phase 2 确认门），Git 政策按"操作"确认（commit 一次、push 一次）。同一任务用户要批两次——先批计划、再批提交，这正是"push 点这么多确认"抱怨的根源。
- 例外 A 语义自相矛盾：同一段既有"that instruction IS the consent"又有"take one confirmation"。本会话执行者选了前半句，跳过确认直接执行整个序列。
- 通用硬约束缺失：序列中途失败后 agent 擅自改方式重试（本会话真实事故）、提交消息不呈现导致擅自合并提交与擅自定消息、push 被拒后可能擅自 pull/rebase。
- 写操作列表有缺口：restore、rm 未归类；checkout 未分级——一刀切会与分支工作流冲突（每个任务建分支多一次确认），但携带未提交改动切换确有覆盖风险。

### 提议方案

**方案一：提交前一次确认（核心重写，五个同步点同步改）**

- 唯一确认点 = 提交前命令回显：任何任务（无论规模）完成后、提交前，回显完整 git 命令序列——add 暂存哪些文件、commit 消息（多提交则逐条列出，类型含在消息前缀）、push 目标分支；用户确认一次，覆盖整个序列（add → commit → push）。
- 计划批准降级为意图对齐：中/大型任务的 Phase 2 计划批准只对齐"改什么、怎么改"，不再是提交确认。
- 规模分级降级：规模只决定"要不要写 TASK 计划文档"，不再决定"要不要给用户确认"。
- 此设计消解两个既有隐患：确认点与命令回显绑定，不依赖"分支工作流 + PR 审批"这个隐藏前提；规模不再决定要不要确认，"小型误判"的兜底问题消失。
- release：Proposal 在 Approval Gate 批准后覆盖整个序列（保留现状——它本来就是把完整变更呈现给用户批准的模型）。

**方案二：通用硬约束（无论哪类改动都适用）**

- 回显必须是完整的 git 命令序列：暂存哪些文件、每个提交的消息、目标 remote/branch；用户确认的是该序列，执行不得偏离。
- 序列中途失败条款：任一步失败 → 停止并报告，不得改用其他方式重试、不得即兴修补，重新取得确认后继续。
- 远端拒绝条款：push 被拒（non-fast-forward）→ 停止并报告，不得擅自 pull/rebase 后再推。
- 歧义指令判例：加"提交一下"这类中文歧义例子，仍归"先问"。

**方案三：写操作列表补全**

- restore、rm 补入独立确认列表（有破坏性）。
- checkout 分级：建分支与干净工作区切换归自动（与分支工作流一致）；携带未提交改动切换需确认。
- amend 已推送的提交视同 force push，需独立确认。

**方案四：门禁与验证同步**

- consent 簇门禁标记重设计：按新政策的确认结构——一个授权点（提交前命令回显确认）加两个对齐点（计划批准意图对齐、release Proposal 批准）——重写标记正则，同步点从四处扩为五处。
- 新增测试：命令回显、失败、远端拒绝条款与 checkout 分级标注的存在性断言（防止五处漏改）。
- 被治理项目侧继承：模板与规则改动随 INIT 复制到下游项目，CHANGELOG 说明。

**方案五：提交一致性 hook（可选，默认不启用，定位修正）**

- hook 定位从"授权校验"改为"内容一致性校验"（校验实际提交 = 用户确认过的命令序列对应的内容），与主流 husky/gitleaks 一类的内容校验一致。
- 凭证 .governance/consent.json（git-ignored）记录用户确认过的提交指纹（文件清单 + commit 消息），hook 比对实际提交与指纹，不符即拒绝。
- 脆弱性：指纹比对是状态比对——agent 回显后哪怕改一行，指纹就对不上，hook 误拒；主流 hook 做独立可判检查（lint/密钥/格式），不做状态比对。实施前须评估此脆弱性。
- 边界诚实：凭证由 agent 写入，防"提交偏离已确认的命令序列"，不防"完全绕过确认"；默认不启用。
- **发布前撤出。** 草拟并随一周期上线，随后从发布撤下：凭证实际未进 .gitignore、`consent.json` 缺失时 hook fail-open、且不校验 commit 消息——足以证明其安全声明不实，不应随版本发布。重做归入 `post-review-remediation` 积压；撤出保持载荷干净。

### 风险

- 五处语义漂移：缓解——consent 簇门禁 fail-closed，漏改任一处 gate 红。
- 每个任务都要提交前确认，高频小改动可能觉得繁琐：缓解——小改动回显的命令短、扫一眼即过。
- 重构范围大、测试重写多：缓解——按方案顺序实施，方案一核心先行，方案五独立可选。
- 新措辞破坏门禁正则造成假阳性：缓解——实施顺序是"先验证正则匹配再改文本"。
- 模板改动影响所有下游被治理项目：缓解——CHANGELOG 写明行为变化，属有意重构而非意外。

### 验证方法

- 五个同步点语义一致：gate 新标记全过；回归验证——人为移除任一处标记 → gate 红并指名。
- 场景演练（人工）：任何任务提交前都须回显完整 git 命令等确认——小型 typo 改动也不例外。
- 场景演练（人工）：commit 失败 → 停止报告；push 被拒 → 停止报告；均不得擅自改方式重试或 pull/rebase。
- 新条款存在性：五处均含命令回显、失败、远端拒绝条款关键词（由新增测试断言）。
- hook 一致性校验：实际提交偏离已确认的指纹时 commit 被拒（测试）；一致时放行（测试）。
- `npm run check` 与 `check:all` 全绿；交付对账 gate 通过。
