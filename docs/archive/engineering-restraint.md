### 任务目的

把「Engineering Restraint」原则作为对现有编码规范的窄增补落地，使 Agent 在实现已批准能力时直接、完整地交付，而不添加当前需求、风险或语义未独立证明的机制。本计划自身必须通过机制测试：只增补既有文件一个小节加一行指针，不建新的治理子系统。

### 当前问题

- coding.policy.md 已有相近语义（不引入未被要求的抽象、不做无关重构、依赖与重型机制需说明、遵循架构与语义所有者），但缺少统一的决策检查点，也缺少两条防误用边界（已批准需求优先、语义接缝合法）。
- 本仓库近期出现过多次"为修复机制而继续增加机制"的返工，说明这是需要提醒 Agent 的可泛化行为模式；这些案例仅作为动机，不自动转化为永久门禁或事故专用流程。

### 提议方案

#### 1. 增补 coding.policy.md 一个小节（payload，零新增分发）

在 references/policies/coding.policy.md 增加简短小节「工程克制与机制测试（Engineering Restraint / Machinery Test）」：

- 机制测试：新增任何非平凡之物前自问——"若它今天不存在，当前需求是否仍会独立证明其必要？" 否 → 不加；是 → 用最窄的既有所有者或成熟机制解决；直接实现够用就不插入框架或流程。流程也是机制：计划、门禁、矩阵、审查步骤、检查清单、证据工件与抽象、状态、恢复系统同等举证。
- 操作规则（压缩）：直接完整实现已批准能力，不以"简单"之名削减真实需求；优先既有语义所有者、既有原语、标准/Node/OS 能力、成熟库；偏好有界真实失败而非投机韧性；测试保护有意义契约，不因可测性制造生产 DI/工厂/钩子；证据证明具体主张而非纪念单次事故；既有代码无自动保留特权，也不得无因翻动；未决重大判断升级；授权行为与证明完成后停止。
- 边界一（已批准需求优先）：本规则约束未经批准的新增机制，不否决用户已批准的功能、架构决策、迁移要求、门禁要求或 TASK 计划；若批准方案与工程克制冲突，必须升级决策，不得自行删减需求。
- 边界二（语义接缝合法）：允许为当前需求保留清晰的接口边界、模块边界、扩展点和稳定语义；禁止为尚不存在的消费者实现完整抽象层、配置系统、插件机制、恢复链、通用框架或状态机。

不新建 policy 文件、不动 lifecycle.policy.md：coding 小节已可承载"流程也是机制"一句；若实施中发现无法承载再升级决策，不默认扩展第三个 policy。

#### 2. SKILL.md 指针一行

治理原则（policy 层）增加一行指针（文件 + 章节），不复述内容。机制测试是 Agent 的决策检查，不是文档交付物：不新增 TASK 字段、不要求每个计划写机制证明、不要求额外记录。

#### 3. 明确不做（机制测试的自用）

- 不新增机械门禁、评分、资格矩阵、审查阶段、报告字段、永久 checklist、machinery registry。
- review-manager 不新增问题：policy 已规定决策时自问；只有出现漏检过度工程的具体证据时，才作为现有检查项中的非独立问题补上（不新增阶段/字段/证据/gate）。
- 不新增 init-spec 复制条目、layout 条目、principles index 行——全部经由现有所有者与现有分发。
- 不复制反补丁计划领地（正交触发条件）：准备新增机制由本规则判断，重复失败处理由反补丁协议接管；删除残留归变更归位。

### 风险与决定

- 自讽风险：本计划只增补一个既有文件的小节加一行指针，不新增专门测试；治理价值来自规则文本在决策点的提示，而非新机器。
- 已批准需求边界：Agent 不得借"反过度工程"删减已批准需求；冲突必须升级——防误用的核心边界。
- 语义接缝边界：防止矫枉过正删除合理的接口/模块边界；未来机制需当前证据，未来结构不算缺陷。
- 与反补丁计划的边界（正交触发条件，非上下级）：准备新增机制 → 本规则判断是否有当前依据；已进入修复且出现重复失败 → 反补丁协议接管失败升级与停止条件。两者不构成前后阶段或优先级关系。
- 反补丁协议是修复域的既定操作规则；本规则不负责重新定义其失败升级流程，只审查反补丁协议之外新增的机制。若两者冲突，必须升级，不得本地裁决。
- 无法机械化：判断型原则由审查与批准执行，不由门禁执行。
- Target 判据：both 成立是因为既有所有者已是 payload 并随 INIT 分发（复用既有通道），而非"看似适合所有项目"。
