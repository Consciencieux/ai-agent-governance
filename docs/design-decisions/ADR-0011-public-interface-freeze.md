# ADR-0011：1.0.0 冻结公开接口面，破坏性变更走 SemVer 与迁移


## 背景

0.x 阶段，本 skill 的接口可以随时改：子技能触发词改名、脚本 flag 增删、`init-spec.json` 的输入契约调整、生成产物路径变动，都只需在 CHANGELOG 记一行。这在没有真实使用者时是正确的——迭代速度优先。

但 0.x 后期出现了两类现场证据，说明"随时可改"已经开始产生成本：

- **被治理项目的升级路径不可预测。** MIGRATE 流程要求"对照目标版本 CHANGELOG 的 Added / Changed 条目"生成迁移清单——这意味着任何未标注为破坏性的接口变更，都会在升级时变成无声故障。v1.0.1 的 provenance 陷阱就是这个形状：文档教操作者手改 `headSha`，而 `execute` 会拒绝，每个按文档发布的被治理项目都会撞上。
- **接口面从未被枚举过。** 讨论"这算不算破坏性变更"时，没有一份清单可查；每次都要重新盘点脚本 flag、触发词、artifacts。判断依据不稳定，结论就不稳定。

1.0.0 发布时做了一次完整盘点，这是本 ADR 的直接触发条件：盘点结果需要一个稳定的语义承诺来承载，而不是散落在某次发布记录里。

## 决策

**1. 1.0.0 起，以下类别构成公开接口面，变更受 SemVer 约束。**

| 类别 | 事实源 | 破坏性变更的含义 |
| --- | --- | --- |
| 子技能触发词 | `references/templates/sub-skills.md` | 改名或删除会让用户既有的调用方式失效 |
| INSTALLED 脚本的命令行接口 | 各脚本自身 | 删 flag、改语义、改退出码约定会让被治理项目的自动化断裂 |
| INIT 契约（输入与产物） | `references/init-spec.json` | 改输入名、删产物、改产物路径会让既有项目无法升级 |
| 被治理项目的规则文件路径 | `references/init-spec.json` | 路径变动会让规则引用与 Agent 指令断链 |
| `.governance/` 运行时契约 | `references/init-spec.json` | 字段与文件形状变动会让校验器与状态读取失败 |

**清单本身不写进本 ADR。** 每个类别的当前成员由上表的事实源枚举——ADR 记录的是"哪些类别受保护"这一决策，不是某次盘点的数字。把成员数量写进 ADR 会立刻制造双源：发布后数字过期，而读者不知道该信哪一份。

**2. 破坏性变更必须走 MAJOR + 迁移说明。**

- 破坏性变更进 MAJOR，`Changed` 条目必须说明影响与迁移方式；仅新增能力进 MINOR；修复进 PATCH。
- 被治理项目的升级路径由 MIGRATE 流程承担：跨版本迁移必须覆盖中间版本的接口变化，不得只看首尾。
- 无法提供迁移路径的破坏性变更，必须先升级决策，不得以"用户量小"自行豁免。

**3. 冻结不等于冻死。**

接口可以演进，代价是版本号与迁移说明。本 ADR 约束的是"变更是否被声明和标价"，不是"能不能变"。

## 后果

- 正面：升级路径可预测；"这算不算破坏性变更"有类别可依；MIGRATE 的迁移清单有稳定依据。
- 代价：接口调整的成本上升——改一个触发词从"改一行"变成"MAJOR + 迁移说明"。这是刻意的：成本正是承诺的内容。
- 遗留风险：类别受保护不等于成员被机械枚举。某个类别新增成员时是否同步事实源，仍靠规则与人工审查（参见判断型规则执行缺口的记录）。
