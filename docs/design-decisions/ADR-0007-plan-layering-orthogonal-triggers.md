# ADR-0007: 治理计划分层独立与正交触发（工程克制 × 反补丁）

状态：Accepted（2026-09-04）

## 背景

两份 TASK 计划相继出现：engineering-restraint（工程克制/反过度工程，已实现）与 anti-patch-development（反补丁式开发与测试架构治理，§1–§3 与 §5 机械子集已实现，其余仍为设计）。两者都约束 Agent 行为，存在三种结构性风险：被合并成一个巨型文档、被定义成上下级（宪法/刑法式层级）、或完全独立无衔接（在"测试拆分是否过度设计"这类问题上反复争论）。相关讨论横跨多轮设计评审，本 ADR 记录最终决策与理由。

## 决策

1. **两份计划保持独立，不合并。** 反过度工程是决策时点的判断原则（陈述性，明确无门禁）；反补丁是修复域的操作协议（repairSessionId、失败预算、归属门禁）。合并会让陈述性原则与操作性细则互相污染语气，且执行时产生"先跑哪个"的歧义。
2. **正交触发条件，非上下级。** 准备新增机制 → 工程克制判断是否有当前依据；已进入修复且出现重复失败 → 反补丁协议接管失败升级与停止条件。两者不构成前后阶段，也不存在裁决优先级。
3. **引桥只写边界与升级。** 两份计划的风险与决定章节各写一条互相指向的边界（不复制规则条文）：新增反补丁机制先过机制测试；已批准的反补丁协议不因复杂而被自行删减；冲突一律升级，不得本地裁决。
4. **机制各自单独举证。** 维护负担证据（如 tests/run-tests.js 的单体膨胀与本会话的多项编辑事故）只证明对应机制（测试架构拆分）成立，不捆绑批准整个失败状态体系——repairSessionId、失败预算、债务报告各自回答机制测试四问（解决哪个当前问题、不用它的具体损失、是否已有机制可承载、是否最窄方案）。repairSessionId 自身实现并获批前，不作为机制必要性裁决的记录位置。

## 否决的替代方案

- **完全合并**：执行歧义 + 抽象层级冲突（哲学宣言与操作手册混写）。
- **完全独立无衔接**：边界争论反复重演，两次设计评审已实际发生。
- **上下级关系（宪法/刑法）**：创造未经批准的裁决优先级，与 Rule Priority 系统冲突；且"宪法"地位可能被用来推翻已批准的操作细则，反方向则被细则绕过判断原则。

## 后果

- 边界条文以两份计划为权威（各自的风险与决定章节）；本 ADR 仅记录决策与理由，不复制任何规则，不构成第三事实源。
- 未来新增第三个行为治理计划时，沿用同一模式：独立成文 + 正交触发 + 边界引桥 + 各自举证。
- 冲突裁决一律升级，不在本地；本 ADR 不改变 Rule Priority 系统。
- 工程克制的落地位置维持现状：references/policies/coding.policy.md（payload，随 INIT 分发）+ SKILL.md 政策层指针；不另设 AGENTS.md 第三份正文。
