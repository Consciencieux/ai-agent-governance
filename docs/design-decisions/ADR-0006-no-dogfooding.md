# ADR-0006: 本仓库不狗粮自身治理框架

- 状态：Accepted
- 日期：2026

## 背景

本仓库生产的是一套 AI Agent 治理框架：INIT 为被治理项目生成 AGENTS.md、docs/rules/、feature registry、`.governance/` 状态、CI 与校验器，AUDIT 巡检偏差，RELEASE 走审批门禁发布。

一个反复出现的问题是：**本仓库自己为什么不用这套框架治理自己？** 现状是轻量级治理（release flow + plans/archive + ADR + tests + 门禁脚本），`scripts/verify_governance.js` 在本仓库以默认模式运行必然失败。这个事实此前只在 AGENTS.md 里用一句话带过，不足以支撑决策，导致每次讨论都要重新论证，也让"要不要补齐工件让校验器变绿"成为一个反复被提起的诱惑。

## 决策

**本仓库不使用自身框架进行狗粮验证。** 三条理由，按重要性排序：

**一、风险错配（决定性理由）。** 校验器检查的是**软件项目**的工件风险：ARCHITECTURE.md 是否有真实内容、features 目录是否存在、CI 是否配置。而本仓库的真实失败模式完全不同——已发生的四类事故是：载荷边界被击穿（`_lib.js` 重构让 82/82 全绿的测试放行了会让所有下游项目崩溃的载荷）、跨域规则漂移（v0.9.1 修 consent 例外时四个同步点只改了三个）、CHANGELOG 漏记、既有工件被误删（CI badge）。**校验器对这四类风险一项都不覆盖。** 狗粮验证的结果会是校验器全绿而这些风险照犯——治理剧场，比没有治理更危险，因为它提供虚假保证。

**二、循环依赖。** 若本仓库的治理依赖自身产品，产品的缺陷会先摧毁本仓库的治理能力。`_lib.js` 事故是现成的推演：如果当时本仓库由 INIT 生成的门禁治理，那批改动会先让本仓库自己的校验脚本失效，然后才轮到下游——检测缺陷的机制被缺陷本身破坏。生产者的治理必须独立于在研产品。

**三、形态错配。** 本仓库没有 `src/`，没有可登记的 feature 对象，12 个脚本之间没有组件依赖图可画；三语文档树与生成的 `docs/` 结构冲突；六阶段生命周期加 TASK 计划对"改一行策略措辞"是过度流程。强行狗粮只能产生空壳工件去满足校验器，而这恰恰违反本框架自己的**反虚构规则**（`SKILL.md` § 反虚构规则：绝不虚构功能、所有证据必须是真实命令输出）。

## 后果

- **本仓库治理的定义**：release flow（`references/workflows/release.md`，路径映射见 AGENTS.md）+ 计划与归档（`docs/<lang>/plans/` → `docs/archive/`）+ ADR + 测试套件 + 门禁脚本（`npm run check` 的 fail-closed 组 + `check:all` 的建议组）。
- **`scripts/verify_governance.js` 在本仓库默认模式 exit 1 是特性，不是缺陷。** 不得通过伪造治理工件（空的 features 目录、占位 ARCHITECTURE.md、手造 `.governance/manifest.json`）让它变绿；此规则已写入 AGENTS.md 的验证一节。
- **狗粮的正确形态是验证产物而非治理自身**：本仓库确实要对 INIT 的输出做端到端验证——载荷完整性门禁（生成产物中逐个运行被复制的门禁脚本，断言无 `MODULE_NOT_FOUND`）就是这种验证，它已经落地。这与"用框架治理本仓库"是两件事。
- **门禁按本仓库的真实风险构建，而非照搬校验器检查项**：已落地的有三语结构对等（`check-doc-parity.js`）、仓库布局同步（`check-layout-sync.js`）、计划交付对账（`check-plan-delivery.js`）、载荷完整性（测试套件 payload 组）、跨域规则同步与原则索引指针（`check-doc-consistency.js --gate`）。这些覆盖的正是上文第一条列举的真实失败模式。
- **本决策可被推翻的条件**：若本仓库演化出真实的软件项目形态（出现 `src/`、可登记的 feature 集合、组件依赖图），或校验器的检查项扩展到覆盖上述真实风险，应重新评估并以新 ADR 取代本条。
